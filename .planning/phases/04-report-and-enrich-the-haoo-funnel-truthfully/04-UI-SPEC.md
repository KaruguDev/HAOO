# Phase 4 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Inherits:** `01-UI-SPEC.md` (approved 2026-08-29), `02-UI-SPEC.md`, and `03-UI-SPEC.md` (approved 2026-08-30). Every existing product-page token, focus treatment, form state, disclosure rule, and accessible-name rule remains in force. This contract declares only the Phase 4 additions: the owner-facing aggregate report, the visitor-facing disclosure change that makes the engagement summary real, and the human-readable summary attached to the qualification email.

**Phase 4 has three authored surfaces:**

| # | Surface | Audience | Runtime |
|---|---------|----------|---------|
| A | HAOO funnel report | Product owner only | Locally generated, self-contained HTML file on the owner's machine — **not** part of the published Vite bundle |
| B | Measurement disclosure and visible collection notice | Visitor | Existing React/Tailwind product page (`#qualify`) |
| C | Engagement-summary field in the qualification email | Product owner, via FormSubmit | Plain text assembled in the browser before serialization |

Surface A is a different runtime from Surfaces B and C. It has no Tailwind, no React, and no npm dependency, so its tokens are declared below as literal CSS values that reproduce the inherited scale exactly.

## Visual Direction

### Surface A — HAOO funnel report

The report is a **printed-page-style document of counted facts**, not a marketing dashboard. It reads top to bottom: what this is and when it was generated, what period is selected, the four stages, and the caveats. Every number is an occurrence count of a browser-observable action.

Locked prohibitions — these visual encodings assert a cohort sequence the anonymous event stream cannot prove:

- No funnel silhouette, tapering shape, connecting arrow, or chevron between stages.
- No progress bar, gauge, donut, sparkline, bar chart, or any width/area proportional to a count.
- No percentage anywhere — not conversion, drop-off, share of total, or percentage change.
- No red/green delta coloring and no up/down arrow glyphs. Direction is carried by the `+` / `−` sign and words.
- No "visitors", "users", "people", "sessions", "leads", "customers", "conversions", "drop-off", "journey", or "delivered" in any label.
- No provider logo, brand chrome, illustration, hero image, or raw JSON dump.

The four stages are a **reporting hierarchy** presented as four equally weighted stacked cards in a fixed order. Nothing about their arrangement may suggest that the same browser flowed from one to the next.

### Surface B — visitor disclosure

Unchanged in silhouette from Phase 3: a pale HAOO inset inside `#qualify` holding one always-visible notice and one native expandable block. Phase 4 changes only copy and adds one labelled group. It must not become a consent banner, modal, toggle wall, or live data viewer.

## Spacing Scale

Declared values (all multiples of 4). The report reproduces the inherited scale as CSS custom properties; the product page keeps using the equivalent Tailwind utilities.

| Token | Value | Usage |

| sm | 8px | Table cell vertical padding; gap between a label and its value; compact list spacing |
| control | 8px | Vertical padding for `summary`, period radio labels, and the disclosure clear control |
| md | 16px | Default paragraph, row, and table cell horizontal padding; gap between stage cards |
| lg | 24px | Card padding below `md`; gap between report header, period control, and stage list |
| xl | 32px | Card padding from `md` upward; gap between major report regions |
| 2xl | 48px | Report top/bottom page padding from `md` upward; existing mobile section spacing |
| 3xl | 64px | Existing desktop section spacing |

Exceptions:

- Every interactive target — `summary`, each period radio label, and every inherited control — has a minimum 44px height. Accessibility target, not a layout token.

- The scrollable table wrapper (see Responsive Layout) may use a `1px` bottom border as a scroll affordance boundary.

Layout rules:

- Report page padding is 24px below `md` and 48px from `md` upward, with 16px minimum at 320px.
- Stage cards are separated by 16px; the group of stage cards is separated from the period control by 24px and from the caveat block by 32px.
- Table rows use 8px vertical and 16px horizontal cell padding; the header row keeps the same padding.
- Surface B keeps the Phase 3 rules verbatim: 16px between the notice and `details`, 24px between disclosure groups, 8px between a group heading and its list. The new summary group inherits those values and adds no new spacing.
- No arbitrary spacing value beyond the 44px target and the 880px measure.

## Information Architecture and Responsive Layout

### Surface A — report document order

1. `h1` — report title.
2. Metadata line: generation timestamp, reporting timezone, site scope. Provider configuration state is deliberately absent — the report cannot observe it (see Metadata row below).
3. Reporting-period control: a `fieldset` with `legend` `Reporting period` containing four radio inputs — `Last 7 days`, `Last 30 days`, `Last 90 days`, `All time`. `Last 30 days` is checked by default.
4. Four period sections, **all pre-rendered into the document**. Each has an `h2` naming the period and its exact inclusive start and end dates, and — for the three bounded periods — the exact inclusive dates of the immediately preceding equal-length comparison period. The all-time section states its first-recorded-event date and renders **no** comparison.
5. Inside each period section, four stage cards in this fixed order:
   1. `Discovery`
   2. `Brochure interest`
   3. `Qualification`
   4. `Assisted and self-onboarding`
6. Caveat block (always last, always visible in every period section's ancestor document, never inside a collapsed element).

### Stage card structure

```html
<details class="stage">
  <summary>
    <h3>Brochure interest</h3>
    <span class="stage-total">124 recorded actions</span>
    <span class="stage-change">+18 vs previous 30 days</span>
  </summary>
  <p class="stage-clarifier">Total of the recorded actions listed below. …</p>
  <div role="region" aria-labelledby="…" tabindex="0" class="table-scroll">
    <table>…</table>
  </div>
</details>
```

- Stage cards are collapsed by default so the opening view stays compact (D-02).
- The expanded table has columns `Recorded action`, `This period`, `Previous period`, `Change`. The all-time table renders only `Recorded action` and `All time`.
- Every event row for a stage always renders, including rows whose count is `0`. A missing goal row from the provider normalizes to `0`; an unknown goal row is a generation failure, not a rendered row.
- Event labels are exactly the ten literal labels in the Copywriting Contract below. Event identifiers such as `haoo_brochure_open` never appear in the rendered report.

### Period switching without JavaScript

The generated report contains **no script element**. Period selection is native radio inputs plus a CSS `:has()` rule on the document that exposes only the section matching the checked input.

- Fallback contract: if `:has()` is unsupported or CSS fails to apply, **all four period sections remain visible and readable in sequence**, each under its own `h2`. Nothing is hidden by `hidden`, `display:none` inline attributes, or markup omission. Degradation must never produce an empty or misleading report.
- Radio inputs remain real, labelled, keyboard-operable inputs. Do not add `role="tab"`, `aria-selected`, or key handlers; native radio-group arrow-key behavior is the interaction.
- `@media print`: hide the period control chrome, keep the header metadata and caveat block, and print the currently selected period section.

### Responsive behavior

- One column at every width. Content measure caps at 880px and centers.
- The stage table sits in a keyboard-reachable scroll region (`role="region"` + `tabindex="0"` + accessible name from the stage heading) so a four-column table can scroll horizontally at 320px without the document itself scrolling horizontally. The page body never scrolls horizontally.
- `summary` contents wrap onto multiple lines below `md`: heading, then total, then change. From `md` upward they may sit on one row with the total and change right-aligned.
- Period radio labels wrap within their fieldset; they never shrink below the 44px target and never overflow.
- No entrance animation, no height animation on disclosure, no transform. Optional hover/focus color transitions are ≤200ms and are disabled under `prefers-reduced-motion`.

### Surface B — disclosure order change

The Phase 3 fixed order is preserved, with step (f) replaced:

- (f) becomes a labelled group `What we attach to your form submission`, containing the summary-content list and the boundary line from the Copywriting Contract. It sits after `What we never collect for measurement` and before the `Clear what this page remembers` control.
- The always-visible collection notice keeps its position immediately above the submit control and remains wired into the submit control's accessible description.
- **Locked prohibition:** the disclosure describes what the summary contains in fixed copy. It must **not** render the live generated summary string, the visitor's current visit band, their flags, or accepted campaign values back to them. This preserves the Phase 3 rule against reflecting runtime measurement values into the page.

## Interaction Contract

### Report

- Stage cards are collapsed by default and toggle through native `summary` activation. No custom open-state mirror, no `role="button"`, no `aria-expanded`, no key handlers on `summary`.
- The expand affordance exposes open/closed state without relying on color alone — the native marker is retained, or a styled marker that also changes shape/rotation.
- Changing the period radio exposes a different period section. No content is re-fetched, re-computed, or animated; all four sections already exist in the document.
- The report has no refresh button, no live indicator, no auto-reload, and no timer. Freshness is the printed generation timestamp only.
- Focus is never moved programmatically. Tab order is: period radios → each stage `summary` in document order → each expanded scroll region.

### Report generation failure

- The generator queries and validates every required range first, renders the complete document in memory, writes a temporary sibling file, then renames it into place.
- Any failed query, unknown goal row, duplicate goal row, non-integer count, or negative count aborts with a nonzero exit and **leaves the previous report file byte-identical**. A partial, stale-mixed, or half-written report must never exist.
- Failure copy is printed to the terminal, not written into the HTML. The owner never opens a report that silently reports fewer periods than it claims.

### Qualification submission (Surface C)

- The engagement summary is built from the bounded context and campaign snapshot **immediately before** `JSON.stringify`, and the existing order is preserved: build body → serialize → emit `haoo_qualify_submit` → `fetch`.
- Summary construction must never block, delay, disable, or fail the submission. If context cannot be read, the field carries the truthful fallback sentence from the Copywriting Contract rather than being omitted silently or throwing.
- The summary never enters an analytics event; the analytics seam remains event-name-only. No provider data is read to build the summary.
- No new visible UI state accompanies the summary. The existing submitting, success, and error states are unchanged, and the confirmation copy still describes a browser-observable send, not inbox delivery.

### Disclosure (Surface B)

- Behavior is unchanged from Phase 3: collapsed by default, native toggle, footer link opens the same instance without moving focus, and opening the disclosure is never itself measured.
- The clear control's behavior, copy, statuses, and idempotence are unchanged. Clearing context does not clear a submitted enquiry or an already-sent summary, and the disclosure must not imply that it does.

**Source:** CONTEXT D-02, D-03; `04-RESEARCH.md` Pattern 4, Pattern 5, and Anti-Patterns; inherited `03-UI-SPEC.md` Interaction Contract.

### Caveat block copy

```
These counts are occurrences of browser actions, not people, sessions, or enquiries.
One browser can appear in several stages, and a repeated action counts again.
A stage total is the sum of the actions listed inside it, not evidence that the same
person moved from one stage to the next.
A validated form send attempt is a request the browser made; it is not proof that the
message reached the inbox.
An outbound click records that a link was opened; it is not a conversation, a
registration, a customer, or completed onboarding.
Browser privacy settings and content blockers can prevent an action from being
recorded, so real activity can be higher than the counts shown.
```
