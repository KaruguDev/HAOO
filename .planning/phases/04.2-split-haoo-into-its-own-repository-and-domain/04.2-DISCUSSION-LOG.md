### Consequences the downstream plans must absorb

Both non-default answers have fan-out the plans were not written for. Neither is a blocker; both
are work the affected plans must now do rather than skip.

- **b (assets move to root).** The default existed to keep `PRODUCT_ASSETS`, the `alternate` href,
  the five `noscript` hrefs, `pdfHref`, `previewImageHref` and `downloadName` byte-unchanged. Moving
  the assets invalidates that: every one of those literals is now an edit, and **both SHA-256 pins
  are invalidated and must be re-derived** against the moved files. Plans 04.2-02 and 04.2-03 own
  this. The exact root-level asset directory is not yet fixed — task 3 must record it before any
  file moves, since it is the string all of the above resolve against.
- **d (retired assets 404).** Every already-published brochure URL under
  `zero-paperhub.com/products/haoo/` breaks at cutover, including the `alternate` link crawlers have
  indexed. This is the accepted cost. Two upsides: the ZPH tree stays ~2.3 MB smaller, and the
  SPLT-01 disjointness check in plan 04.2-08 needs no asset exception in `shared-scaffold.txt`.
- **d does not repeal D-12.** D-12 (meta-refresh stub with canonical at the retired
  `/products/haoo/` path) still stands — it is about the retired *page*, not the four *asset files*.
  Plan 04.2-07 keeps `public/products/haoo/index.html` and drops the four assets; the stub's links
  must point at the new root-level `haoo.online` asset URLs from b, not at the dead ZPH paths.
- **Amended PROD-02 cannot cite Google's site-move retention guidance.** That wording was written
  for the copy-and-retain default. Under d there is no retention period to state; the requirement
  must describe the 404 disposition instead. Plan 04.2-01 task 3 owns this.

### Repository created ahead of plan 04.2-02

`KaruguDev/HAOO` was created empty and **private** at the owner's instruction, before the task 1
domain gate cleared. This does not conflict with plan 04.2-02 — that plan pushes a pruned clone into
this repository, and an empty repository is exactly the target it expects. It also does not advance
the domain gate: GitHub domain verification is profile-level and never required a repository
(GitHub Pages docs, "Verifying your custom domain": *"Domain verification doesn't take place in
repository settings."*).

**Open risk — private repository + GitHub Pages.** Publishing Pages from a private repository
requires a paid plan (Pro/Team/Enterprise). The account plan could not be read to confirm: the `gh`
token lacks the `user` scope, so `gh api user` returns `plan: null`. If the account is on the free
plan, the deploy in plan 04.2-02 will fail at publish time and the repository must be made public
(or the plan upgraded). Resolve before plan 04.2-02 runs.
