<objective>
Clear the two gates that every other plan in this phase is blocked on, and write the split contract
that every other plan reads.

Gate one is not optional and not deferrable: the HAOO domain is, right now, serving a third party's
GitHub Pages content. Gate two is the set of structural choices whose fan-out is large enough that
making them per-file would guarantee disagreement between the canonical URL, the social metadata,
the form source line, the ZERO-PAPER HUB card link and the recovery document's target.

Purpose: no executor can reclaim a domain, and no plan should re-derive a one-way choice.
Output: a cleared domain claim, a recorded contract, and four requirement statements that are true
of the arrangement this phase is building rather than the one it is leaving.

<task type="checkpoint:human-action" gate="blocking-human">
  <name>Task 1: Reclaim the HAOO domain, verify both domains, and decide mail routing</name>
  <what-blocked>
Every task in plans 04.2-02, 04.2-03, 04.2-07 and 04.2-09 that publishes to, asserts about, or
configures the HAOO domain. Success criteria 2 and 3, and requirements SPLT-02 and QUAL-04, cannot
be satisfied while the domain is claimed by someone else.

This is `checkpoint:human-action` and not `checkpoint:human-verify` deliberately. The project's
`workflow.human_verify_mode` is `end-of-phase`, which defers human-verify checkpoints to the end of
the phase — and deferring this one would let the entire phase execute against a hijacked domain. It
also carries `gate="blocking-human"`, so auto-mode cannot clear it either. There is no CLI path:
GitHub domain verification is an account-level web-UI action.
  </what-blocked>
  <why-human>
Measured 2026-09-05 (RESEARCH §URGENT): `www.haoo.online` returns HTTP 200 from GitHub Pages
serving Indonesian gambling SEO spam, under a Let's Encrypt certificate issued 2026-09-03 covering
both the apex and the `www` name. No repository under the KaruguDev account has a Pages site on that
domain. `dig +short _github-pages-challenge-karugudev.haoo.online TXT` is empty — the domain is
unverified, which is exactly the documented precondition for a GitHub Pages dangling-domain
takeover. The DNS is already correct and under the owner's registrar control; the failure is one
layer up, in a Pages claim held by another account.

Per GitHub's own documentation, verifying an unverified domain under your account **immediately
releases** it from any Pages site owned by another account. Verification is per-account, is
performed in the GitHub web UI, and cannot be done by `gh` or by any executor.
  </why-human>
  <action>
The executor performs no repository work in this task. Its whole job is to present the instructions
below, halt, and refuse to proceed until the four command outputs in the verification block are
supplied. If the outputs are absent, incomplete, or show a success status on either HAOO name, the
executor halts again rather than continuing — a 200 on the HAOO host means the third-party Pages
claim is still live and every dependent task would run against someone else's site.
  </action>
  <instructions>
**A. Reclaim the HAOO domain (blocking).**
1. GitHub → your account **Settings** (not the repository settings) → **Pages** → **Add a domain**.
2. Enter `haoo.online`. GitHub generates a TXT record name and value.
3. Namecheap → Domain List → `haoo.online` → Manage → Advanced DNS → add the generated
   `_github-pages-challenge-karugudev` TXT record.
4. Return to GitHub and click **Verify**.

**B. Verify the ZERO-PAPER HUB domain in the same sitting (risk control).**
`zero-paperhub.com` was measured unverified too. It serves production today, and this phase
reconfigures its Pages site — which is precisely the class of change that leaves a domain dangling.
Repeat step A for `zero-paperhub.com`. Two minutes, removes a live risk.

**C. Two findings to decide on, not to fix here.**
- **The HAOO domain has no MX records.** `dig +short haoo.online MX` returns nothing, while
  `zero-paperhub.com` has MX at `privateemail.com`. `info@haoo.online` is the destination of the
  qualification form fallback, the `mailto:` onboarding link and four `noscript` recovery links.
  With no MX, RFC 5321 implicit-MX fallback sends mail to the A record, which is GitHub Pages, which
  runs no SMTP — so mail to that address very likely does not arrive. This is pre-existing and
  formally belongs to Phase 5 / LEAD-07, but you are already in the DNS panel. **Decide the routing;
  the plan does not fix it for you.** (RESEARCH assumption A7: inferred from DNS, not confirmed by a
  test send.)
- **The attacker's certificate covers both HAOO names until 2026-12-02.** Reclaiming the Pages claim
  does not revoke it. Nothing in this phase depends on revoking it; you are being told it exists so
  you do not discover it later in a CT-log monitor. (RESEARCH assumption A1 — GitHub's revocation
  behaviour on a released domain was not confirmed by any authoritative source.)
  </instructions>
  <verification>
Paste the output of all four commands. All four must hold.

```
dig +short _github-pages-challenge-karugudev.haoo.online TXT        # non-empty
dig +short _github-pages-challenge-karugudev.zero-paperhub.com TXT  # non-empty
curl -s -o /dev/null -w '%{http_code}\n' https://www.haoo.online/   # 404
curl -s -o /dev/null -w '%{http_code}\n' https://haoo.online/       # 404 or 301 to a 404
```

A `404` on the HAOO names is the success signal, not a failure: an unclaimed host at the GitHub
Pages edge returns 404. Any 200 means the third-party claim is still live and the phase is still
blocked. Also state the mail-routing decision from step C in one line so plan 04.2-04's disclosure
checkpoint can reference it.
  </verification>

<task type="checkpoint:decision" gate="blocking-human">
  <name>Task 2: Settle the four structural choices with phase-wide fan-out</name>
  <decision>
Four choices that must be made once, together, before any file moves: (a) which leg of the HAOO
domain the Pages site claims, (b) where the HAOO document is published inside its own repository,
(c) what the new repository is called, and (d) what happens to the four assets published under the
retired path.
  </decision>
  <context>
Each of these fans out across many files, and RESEARCH measured that making them implicitly is how
the canonical URL, the two Open Graph URLs, the Twitter image, the form source line, the ZPH card
link, the `CNAME` file and the recovery document's target end up disagreeing about one hostname.
(b) alone touches four asset-path constants, an `alternate` link, five `noscript` hrefs, the
brochure download name and one test case's name. (c) has a live ambiguity: a private repository
`KaruguDev/Lipa-Nyumba` exists, was last touched 2026-08-28, is thematically adjacent, is not the
HAOO site and has no Pages site — it may or may not be the intended home. (d) is a gap the phase
context does not cover and lands squarely on the QUAL-04 amendment in task 3.
  </context>
  <options>
    <option id="recommended">
      <name>The planner's recommendation — take all four defaults</name>
      <pros>
(a) **Apex `haoo.online`.** It matches the product's existing identity (`info@haoo.online`,
`manage.haoo.online`), it is what every planning document already writes, GitHub supplies the
`www` → apex counterpart redirect automatically, and the apex leg already carries both A and AAAA
records. Zero DNS work either way; this needs no new record.

(b) **The HAOO document becomes the HAOO repository's root `index.html`, published at
`https://haoo.online/` — and the four assets stay at `public/products/haoo/`, published at
`https://haoo.online/products/haoo/…`.** Root for the document is conventional for a single-product
site and makes direct-navigation-and-refresh trivially true (it is the site's only document).
Keeping the assets at their existing relative path is the load-bearing half: it leaves
`PRODUCT_ASSETS`, the `alternate` link href, all five `noscript` hrefs, the brochure `pdfHref`,
`previewImageHref` and `downloadName` byte-unchanged, keeps both SHA-256 pins meaningful, and — the
strongest reason — makes a bookmarked asset URL map one-to-one across the two hosts, so the retired
path and the new path differ only in hostname.

(c) **A new repository, name recorded at approval.** Do not reuse `Lipa-Nyumba` without an explicit
decision; a fresh repository has no prior Pages history to unlink.

(d) **Copy the four assets into the ZERO-PAPER HUB `public/products/haoo/` tree and keep them for at
least one year**, alongside the recovery document. A static host emits no per-path redirect, so a
bookmarked brochure URL either resolves or 404s; the PDF URL is published in shipped HTML and is
exactly the kind of link a crawler or a prospect already holds. One year matches Google's own
site-move retention guidance, which the amended PROD-02 will state.
      </pros>
      <cons>
(b) renames one existing test case (`emits a physical nested HAOO document` — the document stops
being nested) and retires the ZPH-shaped root-metadata case in the HAOO repository in favour of a
successor asserting the HAOO root document. Both are recorded narrowings, not losses.
(d) duplicates ~2.3 MB of assets into the ZERO-PAPER HUB tree and duplicates the brochure preview
that the Products card also renders. The duplication is deliberate and must be named in
`shared-scaffold.txt` reasoning so the SPLT-01 disjointness check does not read it as a violation.
      </cons>
    </option>
    <option id="www-leg">
      <name>Claim `www.haoo.online` instead of the apex</name>
      <pros>Matches the ZERO-PAPER HUB site's existing `www.` pattern; apex redirects to it automatically.</pros>
      <cons>Contradicts every literal already written across `.planning/`, the product's own contact surface and the recovery document drafts. Purely a habit match; RESEARCH found no measured constraint favouring it.</cons>
    </option>
    <option id="nested-path">
      <name>Keep the HAOO document at `/products/haoo/` on the HAOO domain</name>
      <pros>Zero changes to the document path, the case name, or the Vite input shape; the retired path maps one-to-one including the document itself.</pros>
      <cons>A single-product site whose only page is three levels deep, with an empty site root. Direct navigation to `https://haoo.online/` would 404. Fails the plain reading of success criterion 3.</cons>
    </option>
    <option id="assets-404">
      <name>Let the four retired-path assets 404 and record it</name>
      <pros>No duplication; the ZERO-PAPER HUB tree stays strictly reduced, which is the cleanest possible SPLT-01 story.</pros>
      <cons>Every already-published brochure link breaks the day the phase lands, including the `alternate` link a crawler has indexed. Cheapest to reverse later, but it is a visitor-facing regression bought for tidiness.</cons>
    </option>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| DNS registrar → GitHub Pages edge | The A/AAAA and CNAME records that route a hostname to GitHub's edge are controlled at the registrar; which repository answers for that hostname is controlled by a Pages custom-domain claim. The two legs are independently mutable, which is the whole takeover surface. |
| GitHub account → GitHub repository | Domain verification is an account-level artifact; a Pages custom domain is a repository-level one. A repository can be deleted while its domain claim's DNS survives. |
| Owner judgment → published privacy statement | The data-controller and relationship copy leaves the repository as a public statement about a visitor's data. Once published it cannot be un-published. |
