<objective>
Make the separation requirement checkable, and check it.

The requirement says neither repository contains the other's source and neither suite reads a file
the other owns. Taken literally that is unsatisfiable: both repositories legitimately need the two
package manifests, three type configurations, four tool configurations, two build and test
configurations, an ignore file, two repository documents, a deploy workflow, an application entry, a
global stylesheet, ambient declarations, a test setup file and a domain file. Toolchain scaffolding
is owned by neither half — it is owned by the repository. A check that treats those nineteen paths as
violations fails for the wrong reason, and a check that fails for the wrong reason gets disabled.

So the allowlist is not a loophole. It is the thing that makes the requirement mean something, and
plan 04.2-01 already wrote it down as a decision rather than leaving it to be discovered here.

Purpose: turn a prose claim into a command with a number in its output.
Output: one auditor, committed identically to both repositories, run green across both checkouts.
</objective>

  <action>
**Write the allowlist first, as a data file with a stated rule.** Create `shared-scaffold.txt` at the
root of each repository, holding the nineteen paths recorded in the split contract, one per line, plus
any duplication that contract recorded — the retained preview image is the known case, and it must be
listed with its reason rather than discovered as a failure.

Above the list, write the closed-list rule in prose, modelled on the doc comment that guards the
focus-source list: an entry is added by declaring toolchain ownership, never by adding a file the
other half also needs. Say plainly what the list is for — that the separation requirement is
unsatisfiable as literally written without it, because both repositories legitimately need the
toolchain, and that a check treating those paths as violations would fail for the wrong reason and
then get disabled.

The two files must be byte-identical across the repositories. A private definition of "shared" in
one repository is the first step to the two trees disagreeing about what separation means.

**Write the auditor, copying the CLI shape wholesale.** The capability-coverage verifier in the HAOO
repository is the exact analog: a version-controlled auditor that reads a file and throws with an
enumerated error list. Copy all four of its properties — the positional-argument path (which is
precisely what makes an auditor relocatable), the usage error, the import guard that keeps the module
importable by a test without running its main routine, and the exit-code assignment rather than a
process-exit call.

Take two required positional arguments, the two checkout paths, and an optional third naming the
allowlist file, defaulting to the one beside the script's own repository root.

**What it checks, in order.**
  1. **The non-empty guard, first.** Read each checkout's tracked-file list. If either is empty,
     fail immediately with a message saying so. Write the same comment the probe case carries: a
     check that compared nothing cannot pass by comparing nothing. This is the single most important
     line in the file.
  2. **The intersection, minus the allowlist.** Sort both lists, take the paths present in both,
     subtract the allowlist by exact whole-line match. Every remaining path is a violation.
  3. **The two positive halves**, which are what the requirement actually asserts. In the
     ZERO-PAPER HUB tree, the set of files whose content names the product, excluding documentation
     and the lockfile, must be exactly the card registry and the recovery document. In the HAOO tree,
     no file under the source directory may name a home-page symbol — the home page component, the
     company-profile download function, or the static navigation collection.
  4. **Exclude the planning directory from all of the above**, with a comment saying why: the
     separation requirement is a claim about what each repository builds and ships, and documentation
     is neither. The planning record's single-home rule is a different decision and is verified
     separately in plan 04.2-09.

**Accumulate, do not short-circuit.** Collect every violation from every check and report them all in
one throw, so one run tells the whole story rather than revealing them one commit at a time.

**Print counts on success.** Report the size of each file list, the number of allowlist entries
subtracted, and the number of paths compared. A success line that says only "passed" cannot be
distinguished from a run that compared nothing — printing the counts is what makes an empty run
visibly wrong even if the guard were ever removed.
  </action>

**Wire the script.** Add a named script to each repository's manifest running the auditor with this
repository first and the sibling checkout second. Resolve the sibling path relative to the repository
root rather than the current working directory, so the command behaves the same from any
subdirectory. Do not add it to either deploy workflow: the check needs both checkouts present and a
CI runner has only one. It is a local and phase-gate command, and the plan summary should say so
explicitly so a later reader does not mistake its absence from CI for an oversight.

**Pin the guard by test, in both repositories.** Add the case named in the phase artifact inventory
to each repository's build-output suite. Import the auditor's checking function directly rather than
shelling out — the import guard exists for exactly this — and assert three things: an empty list on
either side is refused; a path in both lists and not in the allowlist is reported; a path in both
lists and in the allowlist is not reported. Build the fixtures in a temporary directory and remove
them in a `finally` block.

The first of those three is the one that matters most. The auditor's entire value depends on it: if
the non-empty guard is ever removed, every other assertion in the auditor starts passing on nothing,
and this case is what would catch that. Verify it by removing the guard once, watching the case go
red, and restoring it — then record that you did.

**Run the real check and record the numbers.** Run the auditor across both checkouts and record its
full output — the two list sizes, the allowlist entries subtracted, the paths compared, and the zero
violations — in the plan summary. Those counts are the evidence for the separation requirement, and
a later verifier reading the summary should be able to see that a real comparison happened rather
than a trivially empty one.

Record in the deferred-items file that the check is deliberately not in CI, with the reason, so its
