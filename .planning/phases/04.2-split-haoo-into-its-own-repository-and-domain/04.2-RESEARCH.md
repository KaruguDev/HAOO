## Summary

This phase is a **fission, not a rewrite**. Every hard part is bookkeeping under a constraint,
and the constraints are unusually well documented by the phases that preceded it. The
mechanical work is: clone without rewriting history, delete each half from the other, cut
nine measured build-time couplings, re-point sixteen URL literals, and re-establish 44
build-output assertions across two repositories at unchanged strength.

Three things make it harder than it looks, and all three were **measured, not assumed**:

1. **`haoo.online` is currently hijacked.** Both `haoo.online` and `www.haoo.online` resolve
   to GitHub Pages and are served by a *third party's* Pages repository publishing Indonesian
   gambling SEO spam, under a Let's Encrypt certificate issued 2026-09-03 covering both names.
   This is the textbook GitHub dangling-domain takeover, it is live right now, and no plan
   task that publishes to `haoo.online` can succeed until it is reclaimed. The fix is
   documented, free, and takes one DNS TXT record — see §URGENT.
2. **The PostHog project cannot distinguish the two hostnames.** Read from the pinned SDK
   source and this project's own chokepoint: `$host`, `$current_url`, `$pathname` and
   `$referrer` are all set client-side by `posthog-js`, and `stripToBareName` copies exactly
   three property keys into a fresh literal and drops everything else. There is **no host
   dimension on the wire**, therefore none in HogQL. D-11's "handled by a HogQL filter" option
   is not available. Only a timestamp cutover is.
3. **"Neither suite reads a file the other owns" is unsatisfiable as literally written**,
   because both repositories need `package.json`, `vite.config.ts`, `tsconfig*.json` and
   `src/main.tsx`. SPLT-01 needs an explicit shared-scaffold allowlist or it will fail its own
   verification for the wrong reason.

**Primary recommendation:** Sequence the phase as *reclaim the domain → stand up the HAOO
repository and prove the suite green there → re-point URLs in one commit → reduce ZERO-PAPERHUB
→ restate the cross-repository invariants*, and put the domain reclamation FIRST as a blocking
human checkpoint, because it is a prerequisite for four of the six success criteria and it
cannot be done by any executor.

### Why this happened, and why it is the documented case

> "Domain takeovers can happen when you delete your repository, when your billing plan is
> downgraded, or after any other change which unlinks the custom domain or disables GitHub
> Pages **while the domain remains configured for GitHub Pages and is not verified**."
> `[CITED: docs.github.com/en/pages/configuring-a-custom-domain-for-your-github-pages-site/verifying-your-custom-domain-for-github-pages]`

The DNS is under the owner's registrar control (`dns1/dns2.registrar-servers.com`, i.e.
Namecheap), and the CT log shows the owner ran a Pages site on `www.haoo.online` in early 2025.
That repository was removed or unlinked, the DNS records stayed, the domain was never verified,
and on 2026-09-03 someone else claimed it.

### The fix, and it is exactly one action

> "If another user or organization currently uses [an unverified] domain you're verifying, the
> domain will be **immediately released** from GitHub Pages websites which are owned by other
> users or organizations." … "if the domain is already verified by another account, the release
> process will not be successful."
> `[CITED: docs.github.com/…/verifying-your-custom-domain-for-github-pages]`

**Verification is per-account, is done in the GitHub web UI (Settings → Pages → "Add a
domain"), and cannot be performed by `gh` CLI or by any executor.** It requires adding
`_github-pages-challenge-karugudev.haoo.online` TXT with a value GitHub generates.

### What the planner must do with this

1. **Task 1 of the phase is a `checkpoint:human-verify`**: owner verifies `haoo.online` under
   the `KaruguDev` account, confirms `www.haoo.online` returns 404 (released), and only then
   is any HAOO Pages configuration attempted. Every SPLT-02 / QUAL-04 / success-criterion-2
   and -3 task is blocked on it.
2. **Add `zero-paperhub.com` verification in the same checkpoint.** It is measured unverified
   and is exposed to the identical failure the moment ZERO-PAPERHUB's Pages site is ever
   reconfigured — which this phase does. This is a two-minute action that removes a live risk
   on the domain that currently serves production.
3. **The attacker's certificate covers both `haoo.online` and `www.haoo.online` until
   2026-12-02.** Reclaiming the Pages claim does not revoke it. Nothing in this phase depends
   on revoking it, but the owner should be told the certificate exists rather than discover it
   in a CT-log monitor later. `[ASSUMED — revocation is out of the project's control; no
   authoritative source consulted on whether GitHub revokes a released domain's cert.]`
4. **Do not plan around the 24h certificate wait as if it were the long pole.** The DNS is
   already correct for both apex and www; the wait begins when the claim is released.

### Second, independent DNS finding: `haoo.online` has no MX records

```
$ dig +short haoo.online MX      →  (empty)
$ dig +short zero-paperhub.com MX →  10 mx1.privateemail.com. / 10 mx2.privateemail.com.
```
`[MEASURED: dig, 2026-09-05]`

`info@haoo.online` is the destination of `QUALIFY_ENDPOINT_FALLBACK`
(`src/products/haoo.ts:318`), the `mailto:` in `ONBD-03`, and four `noscript` recovery links.
With no MX record, RFC 5321 §5.1 implicit-MX fallback sends mail to the A record — which is
GitHub Pages, which runs no SMTP. **Mail to `info@haoo.online` does not arrive.**

This is pre-existing and strictly speaking belongs to Phase 5 `LEAD-07` ("prove a uniquely
tagged production submission reaches the HAOO inbox"). It is reported here because 04.2 is the
phase that touches this domain's DNS, because D-08's disclosure copy tells a visitor their
details go somewhere, and because fixing MX while the owner is already in the DNS panel
verifying the domain costs nothing. **Flag it in the same human checkpoint; do not silently
fix it — mail routing is an owner decision.**

## Architectural Responsibility Map

| Capability | Primary Tier | Secondary Tier | Rationale |
|------------|-------------|----------------|-----------|
| History preservation across the split | Git / local tooling | — | A pure `git` operation. No CI, no host, no runtime involvement. `git clone` + a deleting commit; nothing else preserves SHAs. |
| Which repository publishes which hostname | GitHub Pages control plane (per-repo custom domain) | DNS (registrar) | The custom domain is a *repository* setting; DNS only routes traffic to GitHub's edge. Both legs must agree, and today the Pages leg is claimed by a third party. |
| Domain ownership / takeover resistance | GitHub account settings (verified domains) | DNS TXT | Verification is an **account**-level artifact, not a repository one. This is why it survives a repository being deleted, and why it is the fix. |
| Retired-path recovery | CDN / Static (the ZPH `public/` tree) | Browser (meta-refresh execution) | GitHub Pages emits no per-path 3xx, so the redirect must be a *published document*. Vite copies `public/` verbatim — that is the only route to a file at a path with no Vite entry. |
| Hostname attribution of measurement events | **Nowhere — capability does not exist** | Report-generation CLI (timestamp bound only) | Measured: the property chokepoint strips every URL property before the wire. Attribution can only be reconstructed from `timestamp`, which lives in the reporting tier. |
| Bounded engagement context continuity | Browser (`localStorage`, origin-scoped) | — | Origin scoping is a browser guarantee, not a project choice. D-10 accepts the consequence rather than defeating it. |
| Build-variable and credential confinement | CI (repository variables) + build (Vite `define`) | Test (`build-output.test.ts` reads the workflow file) | Already correctly tiered today; the split duplicates the tier, it does not move it. |
| Products-card discovery link | Frontend Server / static (ZPH build) | — | D-06 makes this a build-time literal, deliberately severing the cross-repository import. |

### Pattern 1 — Clone-and-prune that keeps every SHA

**What:** produce a second repository whose history is byte-identical to the first and whose
tip commit deletes one half.
**When to use:** exactly D-01's constraint — history must be preserved *and* SHAs must remain
citable.

```bash
# Measured preconditions: origin/main = 7ba2c89, 416 commits reachable from HEAD,
# .git = 32M. [MEASURED: git rev-list --count HEAD → 416; du -sh .git → 32M]
# NOTE: the CONTEXT.md figure of "412 commits" is close but not current; the phase is
# four commits further on. Do not restate 412 as a measurement.

gh repo create KaruguDev/<haoo-repo> --private --confirm      # or via the web UI
git clone git@github.com:KaruguDev/ZERO-PAPERHUB.git haoo
cd haoo
git remote set-url origin git@github.com:KaruguDev/<haoo-repo>.git
git rev-list --count HEAD            # must equal the source count — nothing was rewritten
# ... deleting commit(s) here ...
git push -u origin main
```

**Why this and nothing else.** `git clone` copies the object database; no SHA changes.
A subsequent `git rm` is an ordinary commit *on top of* that history, so:
- `git log --follow src/products/haoo.ts` walks back through every Phase 1–04.1 commit;
- `git blame` on any surviving line resolves to its original commit;
- every SHA cited in `.planning/` still resolves in the new repository.
`git filter-repo` and `git subtree split` both fail the first property.
`[CITED: git-scm.com — clone copies objects verbatim; filter-repo rewrites]`

**Anti-pattern:** cloning with `--depth`. A shallow clone has no history to preserve and
`git log --follow` stops at the graft point. Clone full.

  remains — and the removal must be recorded, not silent.

## Common Pitfalls

### Pitfall 1 — Planning the domain work as if `haoo.online` were free

**What goes wrong:** the plan sets the HAOO repository's custom domain to `haoo.online`, GitHub
refuses or the site 404s, and the executor concludes the DNS is wrong and starts editing
records that are already correct.
**Why it happens:** the DNS *is* correct — A, AAAA and the `www` CNAME are all exactly what
GitHub prescribes. The failure is one layer up, in a Pages claim held by another account.
**How to avoid:** make domain reclamation a blocking human checkpoint that is task 1 of the
phase, with an explicit verification step (`curl -sI https://www.haoo.online/` must return
`404` before proceeding).
**Warning signs:** a `gh api ... /pages` PUT that returns 422; the site serving someone else's
content; `x-github-request-id` present on a response whose body is not yours.

### Pitfall 2 — Choosing apex vs `www` for `haoo.online` by habit

**What goes wrong:** the choice is made to match ZPH's `www.` pattern, or left implicit in the
`CNAME` file, and the canonical URL, the OG URLs, the `sourceNote`, the ZPH card link and the
recovery document's target end up disagreeing about one hostname.

**The measured facts:**
- A Pages site has **one** custom domain, and GitHub supplies the counterpart redirect
  automatically in either direction. `[CITED: docs.github.com/…/managing-a-custom-domain-…]`
- Both legs are already provisioned: apex has A×4 + AAAA×4 at Pages, `www` has a CNAME to
  `karugudev.github.io`. Either choice needs **zero DNS work**. `[MEASURED: dig]`
- **`manage.haoo.online` does not constrain the choice.** It is an independent A record to
  `104.248.156.137` (DigitalOcean) with its own Let's Encrypt certificate. So are
  `check.`, `support.` and `advocate.haoo.online` (all in the CT log). Sibling subdomains are
  independent DNS names; a Pages apex claim does not touch them. `[MEASURED: dig +short
  manage.haoo.online → 104.248.156.137; crt.sh]`
- `haoo.online` has **no MX record**, so no email-routing consideration constrains the apex
  either — unlike `zero-paperhub.com`, which has MX at `privateemail.com`. `[MEASURED: dig MX]`

**Recommendation:** use the **apex, `haoo.online`**. It matches the product's existing identity
(`info@haoo.online`, `manage.haoo.online`), it is what every planning document already writes,

### Pitfall 3 — Assuming a `301` is available on GitHub Pages

**What goes wrong:** someone tries `_redirects`, a `.htaccess` rule, or a `jekyll-redirect-from`
front-matter key, and ships something that silently does nothing.
**Why it happens:** all three are real mechanisms on *other* static hosts.
**The measured/cited truth:**
- GitHub Pages supports no user-supplied server configuration and emits no per-path 3xx.
  `[CITED: docs.github.com — Pages does not support .htaccess or .conf]`
- `jekyll-redirect-from` generates **HTML meta-refresh pages**, not HTTP 301s. Same mechanism
  as D-12, plus a Jekyll build this repository does not run.
  `[CITED: github.com/jekyll/jekyll-redirect-from]`
- The only real 3xx GitHub Pages emits is the automatic apex↔`www` counterpart redirect — a
  *domain-level* behaviour, unavailable for a path.
- **An instant (0-second) meta refresh is read by Google Search as a permanent redirect**;
  a delayed one is read as temporary.
  `[CITED: developers.google.com/search/docs/crawling-indexing/301-redirects]`
  A widely repeated community claim that "meta refresh is a 302 by default" is **contradicted**
  by Google's own current documentation and should not be carried into the plan.
- **Keep the recovery document for at least one year.** "Keep redirects for as long as
  possible, generally at least 1 year."
  `[CITED: developers.google.com/search/docs/crawling-indexing/site-move-with-url-changes]`
  D-12 does not name a duration; the amended PROD-02 should.
- `rel="canonical"` is **complementary, not a substitute**. Google's site-move guidance treats
  redirects and canonicals as different jobs. D-12 correctly ships both.

**How to avoid:** state in the plan that the recovery document is a *client-side redirect used
as a last resort per Google's own guidance*, with the 1-year retention written down.
**Warning signs:** any plan task mentioning `_redirects`, `netlify.toml`, or `.htaccess`.

### Pitfall 4 — Believing the PostHog project can tell the two hostnames apart

**This is the single most consequential technical finding for MEAS-08.**

**What goes wrong:** the plan writes a task like "add a `$host = 'haoo.online'` filter to the
report query", the executor discovers the column is always `NULL`, and either fakes it or
quietly ships a hostname-mixed all-time count under a heading that claims otherwise.

**What was measured, in the pinned SDK and in this project's own chokepoint:**

1. `$host`, `$current_url`, `$pathname` and `$referrer` are **set client-side** by `posthog-js`
   from `window.location`. From the installed `posthog-js@1.425.1` bundle:
   `$current_url:io(…s.href…),$host:null==s?void 0:s.host,$pathname:null==s?void 0:s.pathname`
   `[VERIFIED: node_modules/posthog-js/dist/module.js — grep for `$host`, 2 occurrences, both
   client-side derivations from `location`]`
2. This project's `before_send` reducer copies **exactly three property keys into a fresh
   literal** and returns `null` for anything else:
   ```ts

     'token',
     'distinct_id',
     '$process_person_profile',

   ```
   `[VERIFIED: src/measurement/posthog-lockdown.ts:141-145]`
   and
   ```ts
   const properties: Record<string, unknown> = {};
   for (const key of TRANSPORT_REQUIRED_PROPERTIES) {
     if (!Object.prototype.hasOwnProperty.call(source, key)) return null;
     properties[key] = (source as Record<string, unknown>)[key];

   ```
   `[VERIFIED: src/measurement/posthog-lockdown.ts:175-179]`
   The doc comment is explicit that this is a *fresh literal, never a spread minus a denylist*
   (`:158-163`).
3. The project's own test fixture already asserts the strip by *including* `$current_url` in
   the simulated vendor payload:
   `$current_url: 'https://www.zero-paperhub.com/products/haoo/', $referrer: …, $lib: 'web'`
   `[VERIFIED: src/test/fixtures/posthog-capture-contract.ts:179-181]`
4. The capture entry point takes a **single argument** and no property bag exists to carry a
   host: `capture(event: string): void` `[VERIFIED: src/measurement/posthog.ts:176]`, and
   `sink = (event: string) => { initialized.capture(event); }` `[VERIFIED:
   src/measurement/posthog.ts:506-512]`.
5. The lockdown additionally sets `save_referrer: false`, `save_campaign_params: false`,
   `custom_campaign_params: []`, `disable_scroll_properties: true`, `person_profiles: 'never'`,
   `persistence: 'memory'`, `disable_persistence: true` `[VERIFIED:
   src/measurement/posthog-lockdown.ts:115,121-127]`, so no super-property channel exists either.

**Conclusion, stated plainly as the brief asked:**

> **Hostname is NOT distinguishable in HogQL for this project's events.** The wire payload per
> event is the bare name plus `{token, distinct_id, $process_person_profile}` and the vendor's
> own envelope (`uuid`, `timestamp`). There is no `$host`, no `$current_url`, no `$referrer`.
> A HogQL `WHERE properties.$host = …` filter would match zero rows on every event this
> project has ever sent — including the ones already recorded from `www.zero-paperhub.com`
> since 2026-09-05.

**What that means for `scripts/generate-haoo-report.mjs` and MEAS-08.** The report's SQL is:
```sql
SELECT event, count() AS occurrences
FROM events
WHERE event IN ('haoo_page_view', … ten names …)
  [AND toDate(toTimeZone(timestamp,'Africa/Nairobi')) >= toDate('<start>')
   AND toDate(toTimeZone(timestamp,'Africa/Nairobi')) <= toDate('<end>')]
GROUP BY event ORDER BY event LIMIT 100
```
`[VERIFIED: src/reporting/generate.ts:203-214]`
and separately
```sql
SELECT toString(toDate(toTimeZone(min(timestamp),'Africa/Nairobi'))) AS first_day
FROM events WHERE event IN (…) LIMIT 1
```
`[VERIFIED: src/reporting/generate.ts:236-240]`

The **only** discriminator available is `timestamp`. Two consequences the planner must handle:

- The `'all'` range emits **no bounds at all** (`const bounds = range === 'all' ? '' : …`,
  `src/reporting/generate.ts:204`). Post-split, "all time" silently means "including
  `www.zero-paperhub.com`".
- `firstRecordedDaySql()` has **no bound either**, so the report's "first recorded day" would
  name **2026-09-05** — the ZPH deploy date — and present it as HAOO's own history.

**The recommended handling** (and the good news is that the machinery already exists): add a
repository-owned **cutover day constant** and apply it as a lower bound to *both* queries, so
"all time" means "all time on the HAOO domain". This is a ~6-line change in one file, it is
version-controlled rather than a provider setting, it survives `validateEchoedQuery`
(`src/reporting/query-provenance.ts`) because the bound is inside the submitted query text, and
it makes the truthfulness claim structural instead of a footnote. Pair it with a one-line
provenance statement in the rendered report naming the cutover day and why it exists — MEAS-08
is a requirement about *describing events truthfully*, and "these counts begin at the domain
move" is exactly such a description.

**Do not** solve this by adding a fourth transport property. That reopens the chokepoint that
MEAS-02 and MEAS-03 rest on, and it would be a privacy regression bought to fix a reporting
inconvenience.

### Pitfall 5 — Treating the storage-key rename as a schema-version event

D-10 says the rename "is handled as a schema-version event under Phase 3 D-10". **Mechanically
these are two different operations,** and the difference is worth one sentence in the plan.

**What the code actually does** — all reads go through `config.storageKey`:
```ts
previous = parseContext(storage.getItem(config.storageKey), config, today);
if (previous === null) storage.removeItem(config.storageKey);
```
`[VERIFIED: src/measurement/index.ts:312-313]`
and `parseContext` rejects a version mismatch before anything else structural:
```ts
if (!exactKeys(record, CONTEXT_RECORD_KEYS)) return null;
if (record.version !== config.schemaVersion) return null;
```
`[VERIFIED: src/measurement/index.ts:121-122]`

So:

| Operation | Old record | Result |
|---|---|---|
| **`schemaVersion` bump** (1 → 2), key unchanged | found, version mismatched | `parseContext` → `null` → `removeItem(key)` → `freshContext`. **Old record is deleted.** |
| **`storageKey` rename**, version unchanged | not found under the new key | `getItem` → `null` → `parseContext(null) → null` → `previous === null` → `freshContext`. **Old record is orphaned, not deleted.** |

**Neither crashes.** `parseContext` returns `null` on every malformed, mis-versioned, wrong-key,
expired (`> 180` days, `:131`) or unparseable input, and the `catch` at `:150` swallows a
`JSON.parse` throw. The rename is a **clean reset by construction** — the question the brief
asked is answered: there is no crash path, and no code change is needed beyond the literal.

**But the two mechanisms differ in one visible way, and it is a privacy point:**

At `https://www.zero-paperhub.com`, the existing `zph.haoo.ctx.v1` records will **never be
removed**. After the split that origin serves only the static recovery document, which under
D-12 carries no measurement — and therefore no `clearContext` control either. The visitor's
"clear this record" affordance (`MeasurementDisclosure`'s clear button) leaves with the page.
A record the disclosure promised the visitor could clear becomes unclearable.

Three defensible dispositions, for the planner and the D-09 checkpoint to choose between:
1. **Accept and record it.** The record is bounded, non-identifying, expires after 180 days
   (`EXPIRY_DAYS = 180`, `src/measurement/index.ts:49`) and is unreachable by the new origin.
   Name it as an accepted cost, as D-06 does for card drift.
2. **Have the recovery document remove it.** Four lines:
   `try { localStorage.removeItem('zph.haoo.ctx.v1'); } catch {}`. This is *cleanup*, not
   measurement, so it arguably does not violate D-12's "carries no measurement" — but D-12 also
   says "it is a static document, not a route", and adding script is a widening. **Flag to the
   owner; do not decide it in a plan.**
3. **Bump `schemaVersion` as well as renaming the key**, so any future visitor who somehow
   reaches an old record under an old key gets it removed. Belt and braces; costs nothing.

Option 3 is free and strictly better than the rename alone, and it is the reading that makes
D-10's phrase "handled as a schema-version event" literally true. **Recommend doing both.**

### Pitfall 8 — Pushing the new repository's workflow with the wrong credential

`gh auth status` reports token scopes `'gist', 'read:org', 'repo'` — **`workflow` is absent**.
`[MEASURED: gh auth status, 2026-09-05]`

remote to SSH, and push over SSH. Or re-run `gh auth refresh -s workflow` first.
