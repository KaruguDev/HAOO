<objective>
Make the two visitor-facing statements true of a standalone HAOO domain, and reset the bounded
browser context cleanly at the new origin.

The disclosure today names the processor and the jurisdiction and never names the controller. On the
parent company's hostname the controller was implicit in the address bar; on the HAOO domain it is
stated nowhere. That is the one substantive copy change this phase requires, and it is accuracy
rather than preference: HAOO is a product of a sole proprietorship, not a separate legal person, so
there is no entity for controllership to move to and a domain change does not change who receives
the data.

The storage rename is the smaller half and it is a data edit, not a migration. Browser storage is
origin-scoped, so every existing record becomes unreachable the moment the domain changes — a state
Phase 3 already defines as a legitimate coarse answer.

Purpose: the visitor-facing promises survive the move as true statements.
Output: a controller statement structurally required by the type system, and a clean reset.
</objective>

**Rename the key** off the parent-company prefix, which is a misnomer on the HAOO domain, to a name

short, keep the product and purpose legible, and carry a version token so a future schema change has

**Bump the schema version** in the same edit. These are mechanically two different operations and it
is worth one sentence of comment saying so. A version bump finds the old record and *removes* it; a

returns nothing for a malformed, mis-keyed, mis-versioned, expired or unparseable input, and the
caller falls through to a fresh context. Doing both is free and strictly better than the rename
alone: it means any visitor who somehow reaches an old record under the new key gets it removed
rather than merely ignored.
