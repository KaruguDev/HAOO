## Visual Direction

The `#qualify` section reads as a **written consultation invitation**, not a gate and not a sales form. It sits on the calm light surface between the white brochure section and the navy closing onboarding band, so the page rhythm is: story → brochure → *"or send us the details"* → onboarding choices.

Restraint is the point. One white card on the light page surface, a visible border, three short labelled groups, and one filled action. No progress bar, no step wizard, no multi-page flow, no illustration, no icons inside field rows. Icons appear only in the confirmation and failure panels and in the direct-contact links, matching the existing `OnboardingChoices` treatment.

The section must never out-rank the assisted WhatsApp path. Global assisted-first hierarchy (Phase 1 D-09/D-10) is preserved structurally, not by weakening the submit control:

- The section appears **after** the brochure, so a visitor reaches two full onboarding blocks before it.
- The submit control is filled accent but **auto-width from `md`**, while every WhatsApp action stays **full-width** inside its panel.
- The entry-point link added to all three `OnboardingChoices` blocks is a text link placed **below** the WhatsApp and self-service actions and is worded as an alternative ("instead"), never as the recommended path.

**Source:** CONTEXT D-06, D-07, D-08, D-10; `01-UI-SPEC.md` Visual Direction.

## Spacing Scale

Declared values (all multiples of 4):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Gap between a control and its inline error or help text; icon gaps |
| sm | 8px | Gap between a field label and its control; gap between stacked fallback links |
| control | 12px | Vertical padding inside inputs, selects, textareas, and the submit control |
| md | 16px | Horizontal padding inside inputs, selects, and textareas; default element spacing |
| lg | 24px | Gap between fields inside a fieldset; form card padding below `md`; submit control horizontal padding |
| xl | 32px | Gap between fieldsets; form card padding from `md` upward |
| 2xl | 48px | Mobile section vertical padding (`py-12`) |
| 3xl | 64px | Desktop section vertical padding (`md:py-16`) |

Exceptions:

- **44px minimum interactive target.** Every input, select, textarea, submit control, retry control, and direct-contact link keeps a minimum 44px × 44px hit area (`min-h-11`). This is an accessibility target, not a layout-spacing token. Carried forward unchanged from Phase 1.
- **12px `control` token is new in Phase 2.** Phase 1 shipped it as button padding (`py-3` in `OnboardingChoices` and `ProductPage`); Phase 2 promotes it to a named token so field and button padding are declared rather than incidental. It is a multiple of 4 and introduces no new physical value to the codebase.

Layout rules:

- The `#qualify` section reuses the Phase 1 container exactly: `mx-auto max-w-7xl px-4 sm:px-6 lg:px-8`, `scroll-mt-4`, `py-12 md:py-16`.
- Section lead copy: maximum 680px line width (Phase 1 reading measure).
- Form card: maximum 560px width, left-aligned within the container. A single-column form at a comfortable reading measure — do not stretch the card to the container width.
- Form card padding: 24px below `md`, 32px from `md` upward.
- Confirmation and failure panels use the same 560px maximum width and the same padding, so the swap does not shift the page.
- No arbitrary spacing values beyond the 44px target and the declared tokens.

**Source:** `01-UI-SPEC.md` Spacing Scale; existing `ProductPage.tsx` section conventions (`containerClasses`, `scroll-mt-4`, `py-12 md:py-16`).

Rules:

- **`#DFE4F0` must not be used as an input, select, or textarea border.** It computes 1.27:1 against white and fails SC 1.4.11 for an essential control boundary. The existing company contact form's `border-gray-200` treatment must not be copied onto the product surface. Use `#6E7A94`.
- **No green on the product surface.** The confirmation panel uses the pale HAOO fill `#E9EDFF` with navy text and an accent check icon — not the green success treatment used by the company contact form. Phase 1 forbids green as a competing product-page colour.
- **Colour is never the only error signal.** Every invalid control carries `aria-invalid="true"`, a 2px `#B00020` border, a visible inline message, and a visually hidden `Error: ` prefix inside that message.
- **No new named Tailwind ring token.** Ring colours use the arbitrary-hex form `focus-visible:ring-[#4054C6]` or the already-registered `focus-visible:ring-white`. A named token such as `ring-red-500` throws inside `src/test/focus-contrast.test.ts` rather than failing softly.

## Information Architecture and Responsive Layout

### Placement

1. New `<section id="qualify" aria-label="Send your details" class="scroll-mt-4 py-12 md:py-16">` in `ProductPage.tsx`, positioned **between** the `#brochure` section and the closing `#onboarding` section.
2. New product-nav entry `Send details` → `#qualify`, appended to `PRODUCT_LINKS` after `Brochure` and before `Onboarding`, so the nav order mirrors the page order: Benefits · Capabilities · Brochure · Send details · Onboarding. Present in both the desktop nav and the mobile disclosure menu.
3. All three `OnboardingChoices` positions (`opening`, `mid-page`, `closing`) gain a fourth entry point linking to `#qualify`, rendered **below** the existing WhatsApp / call / email group inside the assisted panel.

### Section structure (fixed order)

1. `h2` — section heading.
2. Lead paragraph (Body, max 680px).
3. Sub-lead paragraph framing the form as an alternative to chatting (Body, max 680px).
4. Required-fields note (help text).
5. Form card (max 560px) containing, in order:
   a. Off-screen honeypot (first child, `aria-hidden`, out of tab order).
   b. Error summary — rendered only after a failed submit attempt.
   c. Fieldset `About you`.
   d. Fieldset `About your portfolio`.
   e. Fieldset `Getting started`.
   f. Disclosure note.
   g. Submit control.
6. Live status region — **rendered outside the form card**, mounted from first render, present in every state.

The live status region sits outside the form because the form is replaced on success (D-03). A region inside the form would unmount at the exact moment it needs to announce.

### Field grouping and order

| Fieldset | Fields in DOM order |
|----------|---------------------|
| `About you` | Full name · Email address · How should we reach you? · Phone number |
| `About your portfolio` | Your role · Organization · How many units do you manage? · Where are your properties? |
| `Getting started` | When would you like to start? · Anything else we should know? |

The preferred-channel select precedes the phone field so the conditional-required flip (D-15) happens *after* the visitor chooses, never retroactively on a field they already left.

### Responsive behaviour

- **Single column at every width.** The form does not become a two-column grid. Ten fields at a 560px measure keep DOM order and visual order identical, which is what the keyboard and screen-reader pass in Phase 5 verifies.
- Controls are 100% of the card width at every width.
- The submit control is full width below `md` and auto width (`w-full md:w-auto`) from `md` upward.
- Direct-contact fallback links stack at every width, each a full-width row with a 44px minimum height.
- No surface in this section may create horizontal page overflow at 320px viewport width or at 200% zoom. The 47-county select relies on native option rendering and must not be given a fixed width that clips the longest option name.

**Source:** CONTEXT D-06 through D-09, D-12, D-15; `02-RESEARCH.md` Component Responsibilities and Pitfall 3; `01-UI-SPEC.md` responsive rules.

## Interaction Contract

### Validation timing (D-22)

- Nothing complains while the visitor is entering a field for the first time. No `onBlur` validation before the first submit attempt.
- On submit, validate every field. If any fail: prevent submission, render inline messages on the invalid controls, render the error summary, and move focus to the summary container.
- After a failed attempt, re-validate a field as the visitor edits it, clearing its message as soon as it becomes valid. The summary updates in place.
- A second failed submit must re-announce. Drive the focus move from an incrementing attempt counter, not from the errors object, so an unchanged error set still re-announces.

### Submission states

| State | Submit control | Form card | Live region text | Focus |
|-------|----------------|-----------|------------------|-------|
| `idle` | `Send my details`, enabled | Visible, editable | `''` | Unmanaged |
| invalid submit | `Send my details`, enabled | Visible, values retained | `''` | Moves to error-summary container |
| `submitting` | `Sending…`, `disabled` | Visible, values retained | `Sending your details…` | Native `disabled` removes focus from the button; this is why the terminal states below take focus deliberately |
| `succeeded` | — | **Replaced** by the confirmation panel | `Your details were sent.` | Moves to the confirmation panel heading |
| `failed` | `Send my details`, enabled | **Retained** with all values intact; failure panel appears below | `We couldn't send your details.` | Moves to the failure panel heading |

- `setValues` is never called in the `failed` branch. Entered values survive by construction — this is what LEAD-05 and WCAG 2.2 SC 3.3.7 require.
- The form is replaced on success specifically to make double submission impossible.
- Success and failure are decided from the HTTP response status alone. Never parse the provider's response body.
- Retry re-submits the retained values without re-entry.

### Conditionally required phone (D-15)

When `How should we reach you?` becomes `WhatsApp` or `Phone call`, the phone field becomes required in **four** places simultaneously:

1. The native `required` attribute.
2. `aria-required="true"`.
3. The visible label — the `(optional)` suffix is removed.
4. A sentence routed through the already-mounted `role="status"` region announcing the change.

Do not rely on assistive technology noticing an attribute flip on a control that is not focused. Reverting the channel to `Email` reverses all four and clears any phone error.

### States and motion

- Default, hover, focus-visible, and active states are distinguishable without relying on scale.
- Control hover shifts the border to `#5F6B84`; control focus draws `focus-visible:outline-none focus-visible:ring-2 focus-visible:ring-[#4054C6] focus-visible:ring-offset-2`.
- Submit hover `#3345A7`, active `#29388A` — identical to the Phase 1 WhatsApp action.
- Disabled submit renders at 70% opacity with `cursor-wait`; the relabel is the primary signal, the opacity is secondary.
- Transitions are opacity/colour only, at most 200ms, disabled under `prefers-reduced-motion: reduce`. No animated spinner, no skeleton, no progress bar — the relabelled button plus the live region carry the in-flight state.
- Panels appear without entrance animation. A reveal transform must never delay access to the retry control or the direct-contact links.

### Navigation and links

- The three product contacts keep their Phase 1 destinations exactly: `whatsappHref` with the fixed compile-time starter text, `tel:+254702188044`, `mailto:info@haoo.online`. No page data, form values, or measurement data may enter any URL.
- The `#qualify` anchor scrolls with the section's `scroll-mt-4` offset and never traps focus.
- No modal, no dialog, no route change, no redirect. The visitor stays on `/products/haoo/` through every state.

## Accessibility Contract

- The `#qualify` section contributes exactly one `h2`. Fieldset groupings use `<legend>`, not headings, so the document outline stays h1 → h2.
- Every control has a matching `<label htmlFor>`. Placeholders never replace labels and are used only where they add a format example.
- `autoComplete` tokens are set on every field that collects information about the *person* (WCAG 1.3.5): `name`, `email`, `tel`, `organization`, `address-level1`. Fields describing the enquiry rather than the person use `off`. The honeypot keeps `autoComplete="off"` so browser autofill cannot mark a real visitor as spam.
- Invalid controls carry `aria-invalid="true"` and `aria-describedby` pointing at the inline message and any help text. `aria-describedby` is assembled by filtering, so an empty string is never emitted.
- Exactly one `role="status"` region exists in the section, mounted from first render and never conditionally rendered. Validation announcements use a separate `role="alert"` inside the error summary. `role` and `aria-live` are never swapped on a mounted node.
- Focus moves deliberately at three moments: to the error-summary container after a failed validation, to the confirmation panel heading on success, and to the failure panel heading on provider failure. Each target carries `tabIndex={-1}`. This also recovers the focus the native `disabled` attribute removes from the submit control while in flight.
- Focus order follows DOM order. The honeypot is removed from the tab order with `tabIndex={-1}` and is off-screen rather than `display:none`.
- Focus indicators are visible on the light section surface, the white card, the pale confirmation fill, and the navy onboarding band. Ring pairings are limited to `#4054C6` on the default white offset and `white` on `#18275F`.
- Every interactive target is at least 44px × 44px.
- Spam control is a honeypot plus provider configuration only. No captcha, no challenge widget, no timing gate — LEAD-06 forbids creating a barrier for keyboard or assistive-technology users.
- Content and actions survive to 200% zoom without loss.
- Error identification never relies on colour alone: `aria-invalid`, a border weight change, a visible message, and a visually hidden `Error: ` prefix all carry the signal.
- With JavaScript unavailable, the `<noscript>` panel surfaces the same three HAOO contacts. No analytics, storage, PDF, form, or JavaScript readiness state may hide, disable, delay, or intercept any onboarding destination.

**Source:** LEAD-03, LEAD-05, LEAD-06; QUAL-02/QUAL-03 quality direction; `02-RESEARCH.md` Pitfalls 3, 9, 10 and Code Examples; `01-UI-SPEC.md` Accessibility Contract.
