  <name>Task 1: BLOCKING HUMAN — choose the successor shape for the expected-red Phase 1 gate (D-16)</name>
  <decision>The shape of the successor to the expected-red Phase 1 gate</decision>
  <context>
    `npm run test:phase1:red` exits 1 in **both** repositories today. That is not a bug in the script:
    it is a RED gate, written to assert that the Phase 1 contract suites *fail*, and those suites now
    pass. So the script does exactly what it was built to do, and the result is a command that fails on
    every run in both trees. This decision has been owed since Phase 04.2 and is recorded as an open
    item there.

    Phase 5 cannot claim every required check passes while this is true, and the project's own rule is
    that a retired check is **withdrawn with a named successor**, never deleted silently — the same
    discipline the script's own header already applies to the entry it dropped during the repository
    split.

    Worth preserving whichever way you go: the script's rejection list for infrastructure-shaped
    failures (unresolved imports, missing modules, syntax errors, no test files found, and the rest),
    its per-repository marker sets, and its non-zero-exit requirement. Those three are the machinery;
    the direction of the assertion is the question.

    The two repositories carry different marker sets — HAOO has three, ZERO-PAPER HUB has one — so
    whichever you choose, both change together and each keeps its own markers.
  </context>
  <options>
    <option id="invert-rename">
      <name>Invert it and rename it — assert the suites pass</name>
      <pros>Keeps every piece of machinery: the infrastructure-failure rejection list still distinguishes a real failure from a broken harness, and the marker check still proves the right suites ran rather than an empty selection. Becomes a genuine gate again instead of a historical artifact. Recommended.</pros>
      <cons>The script's path is on the shared allowlist, so a rename means editing that allowlist byte-identically in both repositories in the same change. Slightly more moving parts.</cons>
    </option>
    <option id="invert-keep-name">
      <name>Invert it but keep the file path and script name</name>
      <pros>Fewest moving parts — no allowlist edit at all. Same machinery preserved.</pros>
      <cons>The name says "red" while the script asserts green. A name that lies is the thing this project's naming discipline exists to prevent, and a future reader would have to open the file to learn what it does.</cons>
    </option>
    <option id="retire">
      <name>Retire it, with the successor named in the record</name>
      <pros>Removes a check whose original purpose has genuinely expired. The Phase 1 suites are already run by the ordinary unit command.</pros>
      <cons>Loses the infrastructure-failure rejection list, which is the part that distinguishes "the contract broke" from "the harness broke" — the ordinary unit command does not make that distinction. The marker check goes too.</cons>
    </option>
  </options>
  <resume-signal>Reply `invert-rename`, `invert-keep-name`, or `retire`. If you pick `invert-rename`, tell me the script name you want; if you have no preference I will propose one and record it as mine.</resume-signal>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| continuous integration → a foreign repository | The job clones a second repository into the runner and reads its file tree |
| shared allowlist → the separation guarantee | Every entry subtracted is a path the separation check stops guarding |
| a failing check → a green claim | A check that fails by design trains readers to ignore failures |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-70 | Tampering | the cloned sibling repository in CI | medium | mitigate | The sibling is cloned shallow and is only read as a file tree — no dependency install and no script execution happens inside it; the disjointness script reads files and reports counts |
| T-05-71 | Elevation of privilege | cross-repository credentials in CI | medium | mitigate | Both repositories are public, so the clone is anonymous and no token with cross-repository scope is introduced into the workflow at all |
| T-05-72 | Tampering | the deploy workflow's published artifact | high | mitigate | The separation check is its own workflow rather than a job in the deploy workflow, and the sibling lands outside the workspace, so no stray checkout can reach the published tree |
| T-05-73 | Repudiation | a silently passing separation check | high | mitigate | No continue-on-error is permitted, asserted against the workflow file; an infeasible checkout is recorded as spot-checked with its measured reason rather than hidden behind a green badge |
| T-05-74 | Repudiation | the withdrawn expected-red gate | high | mitigate | The disposal is written into the script header naming what was withdrawn, the plan, the successor and the byte-unchanged guarantees; the rejection list and marker sets are asserted preserved |
| T-05-75 | Tampering | the shared allowlist diverging | high | mitigate | Both copies are compared byte-for-byte after the change and the disjointness auditor is re-run in both checkouts, so a unilateral edit fails rather than quietly widening what the check stops guarding |
