<objective>
Prove QUAL-02's keyboard half on the live HAOO page and the live Products region: a keyboard visitor
can traverse the whole journey in DOM order, always sees where they are, can bypass the header, and
is never trapped.

This spec adds exactly one thing the existing static suite cannot see — **that an indicator is
actually painted at runtime, in a real browser, under real keyboard modality**. The ratio stays owned
by the static suite in both repositories and is not touched here. Recording that division of labour
in the spec header is what stops the two drifting into contradiction.

Purpose: a declared focus class is not a visible focus indicator until a browser paints it.
Output: `e2e/keyboard.e2e.ts` and `05-EVIDENCE-KEYBOARD.md`.

**Working directory: the HAOO checkout** (05-01, D-01/D-04).
</objective>

## Planner assumptions carried forward (surfaced, not dropped)

- **QUAL-02 / unclassified probe edge (unresolved).** The edge probe could not classify QUAL-02 and
  flagged it for manual review. Reviewed here: QUAL-02's shape is an *interaction-sequence* claim over
  a live DOM, which no data-shape taxonomy covers. The planner's assumption is that a forward
  traversal from document start to document exit, plus a reverse traversal from each stop, is a
  sufficient sample of "navigable by keyboard" — no assertion is made about traversal after arbitrary
  interleaved mouse input, nor about assistive-technology virtual-cursor navigation, which no
  automated harness in this stack can observe.

- **Focus-order coverage on the Products region.** The Products region is a section of a page with no
  main landmark and no skip link. That is a recorded, deferred ZERO-PAPER HUB finding. The traversal
  assertions here therefore start at the Products region container on that surface rather than at the
  document start, and the absence of a bypass mechanism on that page is recorded as an observation,
  not asserted as a failure.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| keyboard modality → computed style | The visible-focus state is only produced under real keyboard input; a scripted focus crosses this boundary and measures a different state |
| browser-built-in viewer → the page | The embedded document viewer is third-party surface inside a page this project ships |
| brochure action → a new browsing context | The open action creates a new tab and therefore an opener relationship |
