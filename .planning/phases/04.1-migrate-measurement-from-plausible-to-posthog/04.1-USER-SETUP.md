## Environment Variables

Five variables in two distinct classes. The class matters more than the names: the first
three are **public build configuration** and the last two are **local process inputs**. They
must never be mixed, and the two classes are set in different places.

### Public build-time configuration (browser)

Vite statically inlines every `VITE_*` value into the published JavaScript bundle. All three
values below are therefore world-readable to anyone who opens the deployed site's assets.
That is by construction, not an oversight: they are **public identifiers, not credentials**.
Never place a secret in a `VITE_*` variable.

| Variable | What it is | Where the value comes from |
|---|---|---|
| `VITE_HAOO_MEASUREMENT_PROVIDER` | The build-time selector for the measurement sink. Its finite accepted set is `none` and `posthog`. Unset, blank, or unrecognised selects the inert no-op sink and the journey works with no analytics at all. | Repository configuration — set it to the literal `posthog` only after the approval below. The value is not read from PostHog. |
| `VITE_HAOO_POSTHOG_TOKEN` | The public project API key that identifies which PostHog project receives events. Accepted only when it matches the exact `phc_` prefix shape; every other value resolves to the empty string and no sink is created. | PostHog → Settings → Project → Project API key |
| `VITE_HAOO_POSTHOG_API_HOST` | The ingestion destination. | PostHog's US ingestion host. See the selection rule immediately below — you are choosing from a fixed list, not supplying an address. |

**`VITE_HAOO_POSTHOG_API_HOST` can only select from the approved list; it can never add to
it.** The approved ingestion origins live in `config/approved-analytics-hosts.ts`, which is
version-controlled and deliberately outside `src/`. Exactly one origin is approved —
`https://us.i.posthog.com` — and the EU origin is deliberately absent rather than
listed-and-unused, so a build cannot be pointed at a region the visitor-facing disclosure
does not name. A value that is not an exact origin match, or that carries a port, a path, a
query, a fragment, credentials, or `http:`, resolves to the empty string and no sink is
created. Approving another origin is a reviewed repository change plus a redeploy. It is
never a deployment-variable edit.

Set all three as GitHub Actions repository **variables** (Settings → Secrets and variables →
Actions → Variables), and pass them through the deploy workflow's `Build` step `env` block
beside `VITE_HAOO_FORM_ENDPOINT` — only after the approval in the next section.

### Local process inputs (owner report)

| Variable | What it is | Where the value comes from |
|---|---|---|
| `POSTHOG_QUERY_API_KEY` | A personal API key used to run the owner report. **This is a secret.** | PostHog → Settings → Personal API keys. See the Report Credential section for the required scope. |
| `POSTHOG_PROJECT_ID` | The numeric project id the report queries. | PostHog → Settings → Project → Project ID (the numeric id in the project URL) |

Both are inputs to the local shell that runs `npm run report:haoo`. **Never prefix either
with `VITE_`**, never add either to the GitHub Actions build environment, never commit
either, and never write either into a generated report. Prefixing one for the browser would
publish a credential into a world-readable bundle in a single step, which is exactly why the
two classes are separated here rather than listed together.

### The four removed variable names are gone

`PLAUSIBLE_STATS_API_KEY`, `PLAUSIBLE_SITE_ID`, `VITE_HAOO_PLAUSIBLE_SRC` and
`VITE_HAOO_PLAUSIBLE_DOMAIN` no longer exist anywhere in this repository. Nothing reads them
and nothing falls back to them.

They can still exist in two places this repository cannot reach: **your own shell
environment, and any GitHub Actions repository variables you already created.** Remove them
from both.

If a stale environment still carries one, `npm run report:haoo` **fails loudly and names the
rename** — for example `Removed environment variables found: PLAUSIBLE_STATS_API_KEY is now
POSTHOG_QUERY_API_KEY` — and writes no report. It deliberately does not tell you the new
variable is merely "missing", because that would send you to create a credential you may
already hold under the old name.

## Project Settings the Code Cannot Assert

This section has no analogue in the Phase 4 setup file, because it is a new category of
owner gate: **a setting that lives in the provider's own UI, outside version control, that a
code-level privacy claim depends on.** Neither entry can be established, observed, or
asserted by anything in this repository.

### 1. Discard client IP data — action required

**Navigate to: PostHog → Settings → Project → Privacy → IP data capture configuration, and
enable the option to discard client IP data.**

**What it prevents.** PostHog enriches every ingested event server-side with geo-derived
location fields computed from the visitor's IP address. That is exactly the class of exact
location value the closed-allowlist requirement (`MEAS-02`) prohibits, and it arrives by a
route **no client-side configuration controls** — it happens after the event leaves the
browser, on the provider's ingestion path.

**Why the code cannot do this.** The SDK's `ip` configuration option is documented by the
vendor as `@deprecated - THIS OPTION HAS NO EFFECT`, and its own docblock redirects to a
custom transformation or this project setting. The only remaining client-side lever is
sending `$geoip_disable` **as an event property** — and this phase has just proved twice,
at the configuration boundary and at the wire, that every event leaves carrying a bare
allowlisted name and exactly three transport keys. Adding a property would break that
contract, and the bare-name contract is the thing the two independent gates exist to
protect.

**If you decline this setting, that is a decision with two costed consequences, not a
no-op.** Both must then be planned and performed before collection is enabled:

1. `$geoip_disable` must be added to the event payload allowlist, which reopens the
   bare-name contract and the two gates that pin it.
2. The visitor disclosure must be amended to name what is retained, because the disclosure
   above currently promises a temporary reference and nothing else. Leaving the disclosure
   as-is while geo-enrichment runs would make it untrue.

Record your answer at the gate in the Verification section. `deferred` is an acceptable
answer and keeps the gate open; it is not the same as `declining`.

### 2. Do not re-enable the capture toggles — acknowledgement only

The adapter sends a closed configuration in which every automatic capture surface is set to
an explicit off, and then **re-reads every one of them off the merged configuration the
vendor produced** before any event sink exists. Among the switches it locks:

- `autocapture`, `rageclick`, `capture_dead_clicks` — DOM click/input/form interaction capture
- `capture_pageview`, `capture_pageleave` — automatic page views and page leaves
- `disable_session_recording` — session replay
- `disable_surveys`, `disable_surveys_automatic_display`, `disable_product_tours` — survey
  and tour surfaces
- `capture_heatmaps`, `capture_exceptions`, `capture_performance` — heatmaps, exception
  capture, and web vitals
- `person_profiles: 'never'`, `persistence: 'memory'`, `disable_persistence: true` — no person
  profile, and no identifier written to this browser

**Why a project-UI toggle cannot silently take effect.** The lockdown also sets
`advanced_disable_flags: true` and `disable_external_dependency_loading: true`, which
short-circuit the remote-configuration fetch that a project-UI toggle would otherwise ride
in on. That fetch is the single mechanism by which a setting changed in the PostHog UI
reaches the running SDK.

**Therefore: no action is required, and turning the remote-configuration fetch back on would
be the single change that breaks this guarantee.** Leave the toggles alone; if a future
change re-enables the configuration fetch, every switch above becomes remotely
controllable again.

## Report Credential

The owner report runs locally and needs one personal API key.

**Create it at: PostHog → Settings → Personal API keys → create a new key.**

- **Scope it to this project only** — not to the whole organization.
- **Grant the single permission the provider's UI labels _Query Read_**, and nothing else.

The scope is described here by the label PostHog's own UI shows, deliberately, rather than by
a machine-readable scope string: the string was inferred by analogy during research and never
read verbatim from an official scope list, so asserting it here would be a claim this project
cannot support. If the key is created with the wrong scope, the first report run fails with a
403 — loudly, at setup time, before anything is written.

**Where the key travels.** `POSTHOG_QUERY_API_KEY` is sent only in an `Authorization` header
on the request to the Query API. It is never written into the generated document, never
printed to standard output, and never reaches the browser bundle. Application code receives
query results through an injected capability and never sees the key or the endpoint at all.

Run the report from a shell that already holds both values:

```bash
POSTHOG_QUERY_API_KEY="$POSTHOG_QUERY_API_KEY" POSTHOG_PROJECT_ID="$POSTHOG_PROJECT_ID" npm run report:haoo
```
