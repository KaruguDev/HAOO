## User Constraints (from CONTEXT.md)

### Locked Decisions

**Migration Shape**

- **D-01:** Full replacement. PostHog becomes the only configurable provider; `MEASUREMENT_PROVIDERS`
  becomes `'none' | 'posthog'`. The Plausible adapter (`src/measurement/plausible.ts`), its entry in
  `config/approved-analytics-script-sources.ts`, the preload-contract fixture
  (`src/test/fixtures/plausible-preload-contract.ts`), its tests, its environment variables, and its
  README / `04-USER-SETUP.md` sections are all removed in this phase. Phase 4 verification claims
  that were stated against Plausible are restated against PostHog rather than left dangling.
  — **Reversibility:** one-way — restoring Plausible would mean re-adding a deleted adapter, its
  approved-origin entry, and its independently-pinned preload fixture, and re-deriving the eight
  gap-closure rounds of Phase 4 behaviour that those artifacts encode.

- **D-02:** `npx -y @posthog/wizard@latest` is used to scaffold — it installs `posthog-js` and
  produces version-current initialization code. Its output is then **conformed to the existing
  measurement seam**, not adopted as written: the adapter lives at `src/measurement/posthog.ts`
  behind `resolveMeasurementProvider`, the confirmed automatic-capture opt-out gate, and the
  `eventSink` seam in `src/measurement/index.ts`. Any direct instrumentation the wizard writes into
  `src/main.tsx` / `src/App.tsx` is reverted. Rationale recorded for downstream agents: the wizard
  wires PostHog's defaults (autocapture on, `$pageview` on, cookie persistence), which are exactly
  the behaviours D-03 requires to be off, and it has no knowledge of this repository's fail-closed
  provider resolution.
  — **Reversibility:** costly — the adapter boundary is referenced by the provider resolution, the
  event sink, and the measurement test suite; relocating initialization to the app root later would
  invalidate the fail-closed provider tests.

**Automatic-Capture Posture**

- **D-03:** All four automatic-capture surfaces must be provably off before any PostHog
  initialization is allowed to complete: (a) autocapture of DOM clicks/inputs/form interactions,
  (b) automatic `$pageview` and `$pageleave`, (c) session recording / replay, (d) surveys, heatmaps,
  exception capture, and web vitals. Locking (d) explicitly is deliberate so that a future PostHog
  default change cannot silently re-enable one of them.
  — **Reversibility:** one-way — any of these capturing even once publishes visitor interaction data
  to a third-party processor that cannot be un-published, and (a) would carry free-text form values
  that `MEAS-02` prohibits outright.

- **D-04:** "Confirmed opt-out" for the purposes of the Phase 4 04-09 gate means **two independent
  gates**, not one:
  1. A configuration assertion at the initialization boundary — the disabling options must be
     present and correct, and their absence fails closed at runtime with no script insertion and no
     event sink returned.
  2. A network-payload regression over every event path — the test asserts that nothing reaches the
     provider except the ten allowlisted bare event names.
  The config gate is what keeps 04-09 failing closed in production; the network test is what catches
  a PostHog version bump or option rename that the config gate would pass. Phase 4 needed three
  gap-closure rounds on exactly this class of drift, and 04-06 already established the pattern of
  pinning a provider contract with an independent fixture.

- **D-05:** If the lockdown cannot be established at runtime — for example the loaded PostHog surface
  does not expose the expected configuration options — the adapter **refuses**: no initialization,
  no event sink, `track()` no-ops, and every visitor action continues to work unchanged
  (`ONBD-05`, `MEAS-07`). The refusal is additionally **surfaced to the owner** rather than being
  silent, because a silently refusing bundled SDK produces a report that reads as zero traffic and
  is indistinguishable from a genuinely dead funnel. Exact signalling channel (console, generated
  report line, or both) is at planning's discretion provided the refusal is detectable.

**Reporting**

- **D-06:** The three MEAS-01 human gates are re-scoped by this migration:
  - *Processor privacy approval* — **re-opened**. PostHog is a different processor in a different
    region with a different retention posture; Plausible's approval is not inherited.
  - *Creating the ten dashboard goals* — **retired by design** if the report queries raw event names
    directly (see Claude's Discretion below). It must be recorded as retired, not left permanently
    open.
  - *Live confirmation that each explicit action emits exactly one name-only event with no automatic
    duplicate* — **kept and strengthened**. This is more important under PostHog than it was under
    Plausible, because autocapture and automatic `$pageview` are precisely what would produce the
    duplicate this check exists to catch.
- **D-07:** The `MEAS-08` live reconciliation gate is re-pointed at PostHog: run the documented owner
  command against the approved project and compare the 7/30/90/all-time counts and dates against the
  raw PostHog dashboard.

**Hosting and Account**

- **D-08:** **PostHog Cloud US** (`us.i.posthog.com`). Analytics data is processed in the United
  States.
  — **Reversibility:** one-way — PostHog does not migrate a project between Cloud regions; changing
  region later means a new project, new keys, and a discontinuity in the owner report's history.
- **D-09:** No PostHog project exists yet. The phase produces owner setup instructions alongside the
  code — create the project, capture the project API key and a scoped personal API key for
  reporting, and set the environment variables — following the pattern
  `04-USER-SETUP.md` established for the Plausible activation.
- **D-10:** Because of D-08, the visitor-facing measurement disclosure
  (`src/components/MeasurementDisclosure.tsx`, plus the disclosure copy in `src/products/haoo.ts`
  and `src/products/copy.ts`) must state that analytics data is processed in the United States.
  This is a copy change to a `MEAS-04` surface that Phase 4 verified, not merely a configuration
  change, and it must be re-verified.

### Claude's Discretion

The user explicitly delegated the following. Each is delegated **with binding outcome constraints**
— research and planning choose the mechanism, not the outcome. These are not open questions and
must not be re-asked of the user.

- **Identifier and person-profile policy.** Outcome required: no stable visitor identifier is
  persisted in the browser, no PostHog person profile is created, and no identity join is possible
  between an analytics event and a qualification submission. `MEAS-02` and `MEAS-03` are the
  governing text. Research determines the exact PostHog option names and whether the identifier is
  suppressed, made non-persistent, or never generated. If the chosen mechanism cannot fully satisfy
  the outcome, that must be surfaced as a blocking finding rather than accepted with a caveat.

- **Event-property policy.** Outcome required: no free-text form value, contact detail, exact
  portfolio or location value, or stable identifier can ever appear on an event, and anything that
  *is* retained must be disclosed to visitors. Research determines whether events are stripped to
  bare names (matching the Phase 3 contract literally) or carry a second explicitly-enumerated
  closed allowlist of properties, and how PostHog's default property set and server-side geo-IP
  lookup are suppressed. Note: retaining any property requires amending `MEAS-02` and the visitor
  disclosure, so bare names is the lower-friction outcome.

- **Campaign parameter handling.** Outcome required: campaign parameters are allowlisted and
  normalized before they reach any provider, and never carry personal information (`MEAS-06`).
  Research determines whether PostHog's own UTM capture is suppressed entirely in favour of the
  existing repo-side normalization, or whether normalized values are passed through as properties.

- **Report query mechanism.** Outcome required: the report still rejects an unknown event name, a
  duplicate row, and a non-integer count before writing anything, preserving the guarantees in
  `src/reporting/stats-response.ts`. Research determines the endpoint — a HogQL aggregate through
  the Query API grouped by event name is the closest structural match to today's single-request
  breakdown and is what would retire the ten-dashboard-goals gate in D-06.

- **Report provenance.** Outcome required: a generated report can never claim a range or project it
  did not actually query, and it fails closed before any write. Research determines the PostHog
  equivalent of `validateEchoedQuery` in `src/reporting/query-provenance.ts`. If PostHog echoes less
  than the Plausible Stats API did, that weakening must be stated explicitly in the report and the
  phase documentation — it may not be dropped silently.

- **Report timezone handling.** Outcome required: the report states which timezone its days are in
  and cannot intermittently fail depending on the time of day. Research determines whether the
  `Africa/Nairobi` assertion is ported to PostHog's project timezone with the same nameable
  mismatch abort, or whether ranges become UTC-bounded and the report says so.

- **Environment variable naming.** Outcome required: `PLAUSIBLE_STATS_API_KEY`, `PLAUSIBLE_SITE_ID`,
  `VITE_HAOO_PLAUSIBLE_SRC`, and `VITE_HAOO_PLAUSIBLE_DOMAIN` are fully removed, and a stale
  environment still carrying the old names fails loudly with a nameable error rather than producing
  a silently empty report. Planning chooses between PostHog-specific and provider-neutral names.

- **Refusal signalling channel** for D-05, provided the refusal is detectable by the owner.

### Deferred Ideas (OUT OF SCOPE)

Three gray areas were surfaced but not discussed, and are left to research and planning within the
boundary above rather than deferred to a later phase:

- How the ten allowlisted HAOO event names map onto PostHog event names (the names themselves are
  fixed by Phase 3 and do not change).
- Whether this phase re-runs Phase 4's verification gates against PostHog or writes its own
  verification.
- Rollout ordering — whether Plausible is removed before PostHog is proven working, or after.

No out-of-scope capabilities were raised during discussion.

## Summary

This is a provider swap behind an already-hardened seam, but PostHog is a fundamentally different
shape of provider from Plausible and three of the repository's existing structural guarantees do not
survive the swap unchanged. Plausible was a *thin remote script with one call signature and no
property bag* — the codebase's name-only contract was enforced by the shape of the vendor API
itself. PostHog is a *large multi-product SDK whose defaults are the opposite of every privacy
decision this project has made*, whose feature set is partly controlled by a **server-side remote
configuration fetch**, and which attaches roughly thirty default properties to every `capture()`
call. The privacy contract therefore stops being a property of the vendor API and becomes a property
of this project's configuration and its `before_send` filter — which is exactly why D-04's two
independent gates are correct and necessary.

Three findings dominate planning. First, **`advanced_disable_flags: true` is the load-bearing
lockdown option**: without it, PostHog fetches remote configuration at init and the project's
server-side settings can enable web vitals, heatmaps, exception autocapture and surveys regardless
of local config — verified in `RemoteConfigLoader.load()`, which returns early only when
`_shouldDisableFlags()` is true. Second, **`before_send` is the only complete property chokepoint**:
`property_denylist` runs *before* `$process_person_profile` is attached, and `sanitize_properties`
is deprecated, so only `before_send` — which runs last, on the fully assembled `{uuid, event,
properties}` payload, immediately before the request is queued — can reduce an event to bare-name
form. It must retain exactly `token`, `distinct_id`, and `$process_person_profile`; dropping the
last of those would silently re-enable server-side person processing. Third, **the existing
provider-unset bundle prohibition explicitly forbids the string `posthog` in every built asset**
(`src/test/build-output.test.ts:203`), and `builtBundleText()` concatenates *every* `.js` in
`dist/assets` — so a bundled SDK, dynamically imported or not, breaks that invariant. It must be
deliberately restated with a narrower, still-meaningful contract, never quietly deleted.

Everything else is mechanical. The Query API's `POST /api/projects/:project_id/query/` with a
`HogQLQuery` grouping by `event` maps cleanly onto the existing `parseGoalCounts` row validator, and
timezone handling gets *better* than it was: HogQL date literals parse in the project's timezone, so
pinning `toTimeZone(timestamp, 'Africa/Nairobi')` inside the SQL makes the report's timezone
repository-owned and removes the mismatch-abort condition entirely rather than porting it.

**Primary recommendation:** Bundle `posthog-js` pinned to an exact version, initialize it
synchronously inside `src/measurement/posthog.ts` with the full explicit lockdown object below plus
`advanced_disable_flags: true` and `defaults: 'unset'`, confirm the lockdown by re-reading
`instance.config` (PostHog's merged-config readback — strictly stronger evidence than Plausible's
`o` slot) before returning any sink, strip every event through `before_send` to
`{token, distinct_id, $process_person_profile}`, and query the owner report through one HogQL
aggregate per range with `Africa/Nairobi` pinned in the SQL.

### Alternatives Considered

| Instead of | Could Use | Tradeoff |
|------------|-----------|----------|
| Bundled `posthog-js` npm import | HTML-snippet delivery of `https://us-assets.i.posthog.com/static/1.425.1/array.js` through the existing approved-origin mechanism | **Preserves 04-08's guarantee intact** and preserves `resolvePlausibleScriptSrc`'s origin+exact-path validation almost verbatim (the path ends in `.js` and can be pinned to an exact version). | `person_profiles: 'never'` + memory persistence | `cookieless_mode: 'always'` | Cookieless writes nothing to the browser at all and disables server-side GeoIP as a side effect, but PostHog then computes `hash(team_id, daily_salt, ip_address, user_agent, hostname)` server-side — an identifier derived from personal data, even if irreversible and daily-rotated. [CITED: https://posthog.com/docs/data/cookieless-tracking] |
| HogQL aggregate through the Query API | Ten dashboard "actions" + the Insights API | Would keep the ten-goal human gate open forever, which D-06 explicitly wants retired, and adds a second stateful thing the owner must configure correctly. |

`--save-exact` is a hard recommendation, not style: PostHog ships multiple `posthog-js` releases per
day, config option names and date-gated defaults have both changed inside the 1.x line, and D-04's
whole premise is that a version bump can silently move a default. A caret range would make the
network-payload regression non-reproducible between `npm ci` runs.

Honest reading of the verdicts: both packages exist, are not deprecated, declare `postinstall: null`,
carry official PostHog source repositories, and `posthog-js` has 12.7M weekly downloads. The `too-new`
signal is triggered by the *latest version's* publish date (yesterday), which is an artifact of
PostHog's release cadence rather than evidence of slopsquatting. It is nonetheless a genuine risk
surface for this project specifically — a same-day release is a release no one has run in anger —
which is a second reason to pin `--save-exact` and to have a human confirm the pinned version at
install time.

`@posthog/wizard` is a **scaffolding tool only**. It must be run with `npx -y` and never added to
`package.json`; its output is then reverted per D-02. The planner should treat "run the wizard" and
"install posthog-js" as two separate tasks so the wizard's transitive tree never enters the lockfile.

### Pattern 2: Confirm the lockdown by re-reading the merged config, not by absence of a throw

**What:** `posthog.init(token, config)` is synchronous, returns the instance, and assigns
`this.config` to the **fully merged** config (defaults + user overrides + renames) before returning.
Re-reading `instance.config` therefore proves the *resolved* values, not merely the values that were
passed — strictly stronger evidence than Plausible's `o` slot, which only proved storage.

**When to use:** This is D-04 gate 1. It must run before any sink is returned.

```ts
// Source: posthog-js@1.425.1 lib/src/posthog-core.js:561-600 (`_init`), and
//   dist/module.d.ts:3311 `init(token, config?, name?): PostHog`
//   dist/module.d.ts:3175 `config: PostHogConfig`

function lockdownHolds(resolved: unknown): boolean {
  if (typeof resolved !== 'object' || resolved === null) return false;
  const c = resolved as Record<string, unknown>;

  return c.autocapture === false
    && c.rageclick === false
    && c.capture_pageview === false
    && c.capture_pageleave === false
    && c.capture_dead_clicks === false
    && c.capture_heatmaps === false
    && c.capture_exceptions === false
    && c.capture_performance === false
    && c.disable_session_recording === true
    && c.disable_surveys === true
    && c.disable_product_tours === true
    && c.disable_conversations === true
    && c.disable_web_experiments === true
    && c.advanced_disable_flags === true
    && c.disable_external_dependency_loading === true
    && c.person_profiles === 'never'
    && c.persistence === 'memory'
    && c.disable_persistence === true
    && c.save_referrer === false
    && c.save_campaign_params === false
    && typeof c.before_send === 'function';
}
```

**Critical:** `_init` returns `this` *without throwing* when the token is blank — it only calls
`logger.critical(...)`. A gate written as "call init inside try/catch and trust a non-throw" would
pass on a misconfigured token. The readback is the gate. This is the same lesson `recordsOptOut`
encoded for Plausible.

**Second, free gate:** the public `init` signature is
`init(token: string, config?: OnlyValidKeys<Partial<PostHogConfig>, Partial<PostHogConfig>>, name?: string)`.
`OnlyValidKeys` makes an **unknown or renamed option a `npm run typecheck` failure**. That is a
build-time partner to the runtime assertion and costs nothing — but it only helps if the lockdown
object is typed as `Partial<PostHogConfig>` rather than widened by `as const` into a structural
literal. Plan for `satisfies Partial<PostHogConfig>`.

### Pattern 3: `before_send` as the sole property chokepoint

**What:** Reduce the assembled payload to bare-name form. `before_send` receives the complete
`CaptureResult` and returning `null` drops the event entirely.

```ts
// Source: posthog-js@1.425.1 lib/src/posthog-core.js:1395-1406 — before_send runs after
//   property_denylist, after sanitize_properties, and after $process_person_profile is
//   appended, immediately before the request is enqueued.
// CaptureResult shape: @posthog/types@1.408.0 dist/capture.d.ts:16-24
//   { uuid: string; event: EventName; properties: Properties; $set?; $set_once?; $unset?; timestamp? }
// BeforeSendFn: dist/capture.d.ts:88 — (cr: CaptureResult | null) => CaptureResult | null

const TRANSPORT_REQUIRED = ['token', 'distinct_id', '$process_person_profile'] as const;

function stripToBareName(result: CaptureResult | null): CaptureResult | null {
  if (result === null) return null;
  // Closed allowlist on the way out as well as the way in: anything PostHog itself
  // emits ($feature_flag_called, $web_vitals, $exception, $pageview, …) is dropped
  // here even if a config default moved.
  if (!HAOO_MEASUREMENT_EVENTS.includes(result.event as HaooMeasurementEvent)) return null;

  const properties: Properties = {};
  for (const key of TRANSPORT_REQUIRED) {
    if (key in result.properties) properties[key] = result.properties[key];
  }

  return { uuid: result.uuid, event: result.event, properties };
}
```

**Why `$process_person_profile` must be retained:** it is appended last in
`calculateEventProperties` with the comment *"add person processing flag as very last step, so it
cannot be overridden"* and is the **only** channel by which `person_profiles: 'never'` is
communicated to ingestion. Stripping it would leave the server to apply its own default and create
person profiles. `property_denylist` runs *before* this append, which is exactly why the denylist is
not a sufficient chokepoint.

**Why `token` and `distinct_id` must be retained:** both live inside `properties`
(`properties['token'] = this.config.token` at `posthog-core.js:1501`; `distinct_id` merged from
persistence properties). An event missing either is rejected by ingestion.

**Consequence for the disclosure:** the event that leaves the page carries a per-page-load
`distinct_id` and the project token. That is more than a literally bare name. The Phase 3 disclosure
sentence — *"These signals are sent as bare names with no form answers or visitor properties
attached."* — remains **true as written** (no form answers, no visitor properties), but the planner
should confirm with the owner whether the per-page-load transport identifier warrants one added
clause. Flagged in Open Questions.

### Pattern 4: One HogQL aggregate per range, pinned to the report's timezone

**What:** Replace the Plausible `POST /api/v2/query` breakdown with a HogQL aggregate that returns
one `(event, count)` row per allowlisted name, in exactly the shape `parseGoalCounts` already
validates.

```ts
// Source: https://posthog.com/docs/api/queries — POST /api/projects/:project_id/query/
//   body { query: { kind: 'HogQLQuery', query: '<sql>' }, name: '<label>' }
//   header Authorization: Bearer <personal API key>, scope "Query Read"
// Timezone: HogQL date literals parse in the PROJECT's timezone; toTimeZone pins it.
//   https://posthog.com/docs/sql/expressions

const sql = `
SELECT event, count() AS occurrences
FROM events
WHERE event IN (${TEN_NAMES_AS_SQL_LITERALS})
  AND toDate(toTimeZone(timestamp, 'Africa/Nairobi')) >= toDate('${start}')
  AND toDate(toTimeZone(timestamp, 'Africa/Nairobi')) <= toDate('${end}')
GROUP BY event
ORDER BY event
LIMIT 100
`;
```

**Why pinning beats porting the assertion.** `src/reporting/generate.ts:44` currently declares
`const REPORT_TIMEZONE = 'Africa/Nairobi';` as *"a repository-owned assertion, so it is checked
against the provider rather than trusted"*, with `TIMEZONE_MISMATCH_REASON_PREFIX` for the abort.
Under PostHog the timezone can be made a property of the *query text* rather than of a remote
setting, which removes the mismatch condition instead of detecting it. The report still states its
timezone; it simply can no longer disagree with the provider. That is a strict improvement and it
retires an entire failure mode. **The bounded windows must still be computed by
`periodWindows(days, today)` with `today` derived in `Africa/Nairobi`**, which `reportDay(date,
REPORT_TIMEZONE)` already does — unchanged.

**Row shape adaptation.** `parseGoalCounts` currently requires
`row.dimensions: [goal]` and `row.metrics: [count]` (`src/reporting/stats-response.ts:35-43`).
The HogQL response returns `results` as **positional arrays** — `[["haoo_page_view", 12], …]` — with
`columns: ["event", "occurrences"]`. Two honest options:

1. **Adapt the row reader, keep every rule.** Change the two shape checks to read a two-element
   positional array, and keep unknown-name / duplicate / non-integer / negative rejection byte-for-byte.
   Preferred: the guarantees, not the wire shape, are what `MEAS-01` depends on.
2. Map the response into the Plausible row shape before parsing. Rejected — it adds a translation
   layer that can itself lose a rejection, for no benefit.

Either way the function must additionally assert `columns` equals the exact expected pair, so a
reordered projection cannot swap the name and the count.

### Anti-Patterns to Avoid

- **Relying on `defaults: '<date>'` from the wizard.** The date-gated defaults are a moving target
  and one of them (`internal_or_test_user_hostname` at `'2026-01-30'`) *enables person processing*.
  Pin `defaults: 'unset'`.
- **Using `property_denylist` as the privacy boundary.** It runs before `$process_person_profile` is
  attached and cannot remove it; it also cannot remove anything an extension adds after it. Use it
  only as belt-and-braces, never as the contract.
- **Setting `ip: false` and believing it does something.** `@deprecated - THIS OPTION HAS NO EFFECT`.
- **Calling `posthog.identify()`, `setPersonProperties()`, `alias()`, or `group()` anywhere.** Any of
  them forces person processing on for the rest of the session regardless of
  `person_profiles: 'never'` (`_requirePersonProcessing`). The adapter must expose only `capture`.
- **Letting the adapter own the report endpoint.** `src/reporting/generate.ts` deliberately carries
  no origin, path, or credential name, asserted by a source test. That stays.
- **Adding a parallel PostHog test suite.** `src/test/measurement.test.ts` already has six provider
  describes (`fail-closed provider resolution`, `name-only provider sink`, `fail-closed provider
  initialization`, `… in the full journey`, `provider failure isolation`, `facade contract under the
  widened provider seam`). Extend them.
- **Deleting the `posthog` bundle prohibition without a replacement.** See Pitfall 1.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Event delivery, batching, retry, compression, `sendBeacon` on unload | A `fetch()` to `/i/v0/e/` from the adapter | `posthog-js` `capture()` | The repo's own `NETWORK_FORBIDDEN` boundary forbids `fetch(`/`XMLHttpRequest`/`navigator.sendBeacon` in every measurement source file (`src/test/build-output.test.ts:90`). A hand-rolled sender would have to breach that boundary and would re-derive retry, batching and payload compression badly. |
| Stripping default event properties | A custom wrapper that builds its own payload | `before_send` | It is the documented last-mile hook and the only place the fully assembled payload exists. A wrapper cannot see properties the SDK adds after the call site. |
| Aggregating counts per range | Fetching raw events and counting in Node | One HogQL `count() … GROUP BY event` per range | The Query API doc states bulk/recurring export of `events` is **not supported**; counting locally would also make the report's numbers this project's claim rather than the provider's. |
| Deriving "today" and the 7/30/90 windows | New date maths | `reportDay()` + `periodWindows()` in `src/reporting/` | Already correct, already tested, already handles the Nairobi offset. |
| Validating the provider's response | Trusting the JSON | `parseGoalCounts` + an echo validator | Both already exist and encode Phase 4's threat model (T-04-04). |
| Atomic report writing | `writeFileSync` onto the destination | The existing reserve-temp → write → rename sequence | Already handles the cross-invocation mutex and the interrupted-run recovery message. |

**Key insight:** the value this repository has accumulated is not in *talking to a provider* — it is
in the ~1,100 lines of refusal logic around that conversation. Every temptation to "just write a
small PostHog client" throws that away. The migration is a substitution at one seam plus a rewrite of
one contract fixture; anything larger is a signal that the seam is being bypassed.

## Common Pitfalls

### Pitfall 1: The provider-unset bundle prohibition forbids the literal string `posthog`

**What goes wrong:** `npm test` fails immediately on installing `posthog-js`, in a test whose name
does not obviously point at the cause.

**Why it happens:** `src/test/build-output.test.ts:203` declares

```ts
const UNCONDITIONAL_ANALYTICS_ORIGINS_FORBIDDEN = [
  /googletagmanager|google-analytics|umami|posthog|segment\.com/i,
] as const;
```

and it is applied twice: to every production source file (`it('keeps analytics origins out of
production source modules')`, line 610) **and** to `builtBundleText()` (`it('ships the unset provider
bundle without identity, property, queue, SDK, or credential seams')`, line 656). `builtBundleText()`
(line 231) concatenates **every** `.js` file under `dist/assets` — so a dynamic
`import('posthog-js')` does not help: Vite emits the split chunk into the same directory and it is
still scanned. The same bundle scan additionally forbids
`/\b(?:visitor|user|device|session)(?:Id|ID)\b/` and `/\b(?:uuid|fingerprint|clickstream|eventQueue)\b/i`,
which a minified `posthog-js` will trip.

**How to avoid:** treat this as a deliberate, documented amendment — the phase's single most
important non-code decision. The replacement invariant must still say something true and falsifiable.
Suggested shape, in descending order of preference:

1. Narrow the unconditional list to the *competitor* origins only (`googletagmanager`,
   `google-analytics`, `umami`, `segment.com`) and add a new, sharper PostHog-specific contract:
   the provider-unset bundle must contain **no PostHog ingestion origin reachable from an
   initialized instance**, proved by a runtime test asserting `createPostHogEventSink` returns
   `undefined` for `provider: 'none'` and that no network call is attempted — plus a chunk-graph
   assertion that the PostHog chunk is not referenced by the entry chunk.
2. Scope the string scan to the **entry** chunks only, and assert separately that the PostHog chunk
   is lazily referenced.

Whichever is chosen, `UNCONFIGURED_PROVIDER_ORIGIN_FORBIDDEN` (`/plausible\.io/i`, line 204, and
exported for reuse) is removed with Plausible, and `REPORT_CREDENTIAL_BUNDLE_FORBIDDEN` (line 207)
needs `/PLAUSIBLE_STATS_API_KEY/` → the new name and `/\/api\/v2\/query/` → the PostHog query path.
Good news, verified by grep against the published bundle: `posthog-js@1.425.1/dist/module.js`
contains **zero** occurrences of `Authorization`, `Bearer `, `document.cookie`, `indexedDB`,
`dataLayer`, `navigator.userAgent`, or `supabase` — so the credential prohibitions and most of
`ALWAYS_FORBIDDEN` survive untouched. It does contain `localStorage`, `sessionStorage`, and
`window.location`, but those lists apply to `src/` sources, not to the bundle.

**Warning signs:** a plan that says "remove the posthog entry from the forbidden list" in one line
with no replacement assertion.

### Pitfall 2: Remote configuration re-enables what local config turned off

**What goes wrong:** heatmaps, web vitals, exception autocapture or surveys start firing days after
deployment, because someone toggled a switch in the PostHog UI — or because PostHog changed a
project-level default. The local config was never wrong; it was simply not consulted.

**Why it happens:** `capture_heatmaps`, `capture_exceptions`, `capture_performance` and
`capture_dead_clicks` all document `@default undefined`, and `capture_performance` explicitly says
*"When `undefined`, fallback to the remote configuration. … If an object, that will override the
remote configuration."* PostHog fetches that configuration at init from
`/array/<token>/config` (or the `.js` variant).

**How to avoid:** two things together, not one. Set every one of the four to an explicit `false`
**and** set `advanced_disable_flags: true`. The second is what makes the first unbypassable —
`RemoteConfigLoader.load()` contains, verbatim:

```js
if (this._instance._shouldDisableFlags()) {
    // This setting is essentially saying "dont call external APIs" hence we respect it here
    logger.warn('Remote config is disabled. Falling back to local config.');
    return;
}
```

**Warning signs:** a lockdown object that omits `advanced_disable_flags`; any config comment implying
"PostHog defaults these off".

### Pitfall 3: `defaults: '2026-01-30'` or later silently enables person processing on localhost

**What goes wrong:** local development and CI create PostHog person profiles, and every event from
those hosts carries `$internal_or_test_user: true` — violating "no person profile is created" in a
way that only shows up in the PostHog UI, never in a test.

**Why it happens:** `internal_or_test_user_hostname` documents
`@default /^(localhost|127\.0\.0\.1)$/ (when defaults >= '2026-01-30')` and *"When the current
hostname matches, `setInternalOrTestUser()` is called automatically on startup, **enabling person
processing** and setting `$internal_or_test_user: true`."* The `@posthog/wizard` writes a `defaults`
date into its scaffold.

**How to avoid:** `defaults: 'unset'` **and** `internal_or_test_user_hostname: null` (the type
documents `null` as the explicit disable). Assert both in the lockdown readback.

**Warning signs:** the wizard's `posthog.init` call kept verbatim; a `defaults` value that is a date.

### Pitfall 4: `property_denylist` looks like the privacy boundary and is not

**What goes wrong:** a denylist that appears complete still ships `$process_person_profile`,
`$is_identified`, and anything an extension appended, and a reviewer reading the denylist believes
the payload is bare.

**Why it happens:** in `calculateEventProperties`, the denylist deletion runs, *then*
`sanitize_properties` (deprecated), *then* `properties['$process_person_profile'] = hasPersonProcessing`
with the source comment *"add person processing flag as very last step, so it cannot be overridden"*.

**How to avoid:** make `before_send` the contract and say so in the code comment. Keep the denylist
only as a redundant second layer, and never let a test assert privacy *from* the denylist.

**Warning signs:** a plan task that lists ~30 property names to denylist.

### Pitfall 5: GeoIP cannot be suppressed from the client without adding a property

**What goes wrong:** every event is enriched server-side with `$geoip_country_name`,
`$geoip_city_name`, etc., derived from the visitor's IP — which is exactly the "exact location value"
class `MEAS-02` prohibits, arriving by a route no client-side config controls.

**Why it happens:** the `ip` config option is `@deprecated - THIS OPTION HAS NO EFFECT`, and its
docblock redirects to *"a custom transformation or 'Discard IP data' project setting."* The only
client-side lever is setting `$geoip_disable: true` **as an event property** — which contradicts the
bare-name outcome.

**How to avoid:** make the **project-level "Discard client IP data"** setting a first-class owner gate
in USER-SETUP (Settings → Project → Privacy → IP data capture configuration), verified by the same
live human gate that confirms one event per action. Do not add `$geoip_disable` to the allowlist
unless the owner declines the project setting — and if they do, the property must be added to the
visitor disclosure.

**This is the one delegated outcome that cannot be fully satisfied in code alone**, and per the
CONTEXT instruction it is surfaced here as a blocking finding rather than accepted with a caveat: the
"suppress server-side geo-IP lookup" outcome is achievable, but only through an owner-performed
project setting, not through the adapter.

**Warning signs:** a plan that claims geo-IP is handled by the init config.

### Pitfall 6: `posthog.init()` does not throw on a bad token

**What goes wrong:** a fail-closed gate written as "call init in a try/catch; if it did not throw,
we are initialized" passes with an empty or whitespace token, and the sink is returned for an
instance that will never deliver anything.

**Why it happens:** `_init` (`posthog-core.js:565-569`) trims the token, and on empty calls
`logger.critical(...)` then `return this`. It also returns early on a second `init` with a different
token, only `console.warn`-ing.

**How to avoid:** the readback in Pattern 2 is the gate, and it should additionally assert
`instance.config.token === expectedToken`. The double-init path is also the PostHog analogue of the
04-12 adopted-versus-installed rule: decide about any pre-existing `window.posthog` **before**
initializing, and refuse a non-callable or foreign global intact.

### Pitfall 7: The Query API is not an export API, and pagination differs

**What goes wrong:** a report design that fetches events and counts locally is rate-limited or
refused, or an `OFFSET`-based paging loop silently returns wrong totals.

**Why it happens:** the docs state the endpoint is *"intended for ad-hoc analytics and embedded use
cases"*, that *"Bulk or recurring exports of `events`, `persons`, or `query_log` are not supported"*,
and that *"OFFSET pagination is not supported for programmatic requests"*. Default row limit is 100;
an explicit `LIMIT` allows up to 50k. Rate limit reported as 2400/hour.

**How to avoid:** the design here is already correct — an aggregate returning at most ten rows, four
range queries per run (7/30/90 current + previous is seven requests today; PostHog can do the same or
fewer). Add an explicit `LIMIT` well above ten so a future eleventh event name cannot be truncated
into a silently-wrong zero, and assert the returned row count is ≤ the allowlist size.

### Pitfall 8: A configured-but-refusing provider previously unmounted the page

**What goes wrong:** enabling the provider makes the HAOO page blank for visitors.

**Why it happens:** `04-VERIFICATION.md:116` records *"with a provider configured, a blocked provider
slot unmounts the product page (gap 1)"* — a defect found in Phase 4 verification on the *enablement*
path, which is exactly the path this phase turns on for the first time.

**How to avoid:** the D-05 refusal path is not merely "return undefined" — it must be exercised by a
component-level test that renders the full journey with a refusing provider and asserts every visitor
action still works (`src/test/measurement-page.test.tsx` is the existing home for this). Treat Phase
4's gap 1 as a known-live regression for this phase, not as history.

### Pitfall 9: `capture_pageleave` is off only *because* `capture_pageview` is off

**What goes wrong:** someone later re-enables `capture_pageview` for a good reason and silently gets
`$pageleave` too.

**Why it happens:** `capture_pageleave` documents `@default 'if_capture_pageview'`.

**How to avoid:** set `capture_pageleave: false` explicitly (as the lockdown object does) and assert
the literal `false` in the readback — not the string `'if_capture_pageview'`.

### Pitfall 10: The disclosure interface has no place to say "United States"

**What goes wrong:** D-10 gets implemented as a hardcoded sentence inside
`MeasurementDisclosure.tsx`, breaking the project's rule that the component renders product data.

**Why it happens:** `ProductMeasurementDisclosure` (`src/products/types.ts:169-195`) has exactly these
members: `summary`, `intro`, `signalsHeading`, `signalLines`, `signalBoundary`, `browserHeading`,
`browserFacts`, `browserBoundary`, `campaignHeading`, `campaignDescription`, `neverCollectedHeading`,
`neverCollected`, `summaryHeading`, `summaryIntro`, `summaryContents`, `summaryBoundary`,
`clearLabel`, `clearSuccess`, `clearBlocked`. There is **no processor, region, or recipient member**
— the existing processor sentence (`qualifyCollectionNoteProcessor()` in `src/products/copy.ts:105`)
names FormSubmit for the *form*, not the analytics provider.

**How to avoid:** add a required member (e.g. `processorHeading` + `processorNote`) to the interface,
so a product configuration that forgets it is a typecheck failure — the same construction the
docblock at `types.ts:182-187` already uses for the summary group. Then render it in the component
and assert it in `src/test/measurement-page.test.tsx`. Also note `MeasurementDisclosure.tsx` is bound
by `FULL_BOUNDARY` in `PRODUCT_SOURCE_BOUNDARY` and by a dedicated assertion at
`build-output.test.ts:738`, so the literal must not be written into the component.
