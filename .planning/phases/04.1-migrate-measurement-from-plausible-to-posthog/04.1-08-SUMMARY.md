# Phase 04.1 Plan 08: Owner Activation and the Restated Phase 4 Claims Summary

**The owner now has one document covering everything the code cannot do for itself, the three Phase 4 human gates are honestly re-scoped rather than silently carried forward, no repository instruction names the removed provider, and the one privacy control that lives in the provider's UI was put to the owner as a blocking decision and answered `enabled`.**

## Accomplishments

- **One activation document, six sections.** `04.1-USER-SETUP.md` covers all five environment variables with their sources and their public-versus-secret status, the PostHog Cloud US project and the re-opened processor approval, the two project settings the code cannot assert, the Query Read personal API key, the five human gates, and the recorded finding that no data migration is required.

- **A new category of owner gate was named rather than buried.** Research flagged server-side geo-IP enrichment as a blocking finding, not an accepted caveat: PostHog derives location fields from the visitor's IP by a route no client-side configuration controls, the SDK option that once suppressed it is documented as having no effect, and the only remaining in-code lever would add a property to the payload — breaking the bare-name contract this phase proved twice. The setup document gives the exact navigation path and costs the declining branch: refusing the setting makes the property-based alternative necessary *and* requires amending the visitor disclosure to name what is retained.

- **The three Phase 4 gates were re-scoped honestly.** Processor privacy approval is RE-OPENED — a different processor, in a different region, with a different retention posture does not inherit the previous approval. The ten-dashboard-goals gate is RETIRED BY DESIGN, with the reasoning recorded in place: the migrated report submits a single HogQL aggregate counting raw event names, so no dashboard goal needs to exist and no activity can be permanently omitted by a goal created late. The one-action-one-event gate is KEPT AND STRENGTHENED, because autocapture and automatic page views are the vendor's own defaults and are precisely what would produce the duplicate the check exists to catch — and because it is the only check that confirms ingestion accepts a payload reduced to three properties.

- **The README carries the same contract in fewer words.** The accepted provider set is now the inert value and the new provider name; the api-host variable can only select from the version-controlled approved-host list, never widen it. The dashboard-prerequisite section is gone, replaced by a pointer to the project settings and the setup document. The credential section names the two new variables, the Query Read scope by the label the provider's UI uses, and the updated invocation. A new paragraph records the delivery-mechanism change — pinned bundled dependency rather than a script from an approved origin — which withdraws the bundle-level origin guarantee, and names its successor.

- **Phase 4's claims were restated, not left dangling.** A dated Phase 04.1 amendment block was appended to `04-VERIFICATION.md`: each verified row that named the removed provider, its adapter file, or its approved origin is restated against the PostHog successor; the capability-audit command is recorded as now validating this phase's coverage matrix; and the Phase 4 gap-1 page unmount is recorded as re-armed as a live regression guard by 04.1-05. No original row was edited and no verdict changed. `.planning/REQUIREMENTS.md` gained one dated status note and no checkbox changed state — the code-level closure this phase delivers is necessary but not sufficient.

- **The blocking gate was put to the owner and answered.** The owner replied `enabled`: *Discard client IP data* is on for the PostHog project, and the automatic-capture toggles are left alone. The answer is recorded verbatim beside the gate it closes, with an explicit note that no automated check contributed to it.

## Deviations from Plan

### 1. The whole-tree name gate is unsatisfiable as literally written — reported, not silenced

The plan's Task 2 gate and plan-level verification both require
`git grep -ril 'plausible' -- src config scripts README.md` to return nothing. It returns five
files. The plan's own `read_first` note anticipated a hit and instructed: *report it rather than
silently delete it here.* That instruction is followed. Every match predates this plan (all five
were already present at `6e5d08d`, before Task 2 ran), and every one is a deliberate artifact of a
*correct* migration rather than surviving instruction:

| File | Line | What it is | Why deleting it would be wrong |
|------|------|------------|-------------------------------|
| `scripts/generate-haoo-report.mjs` | 97–100 | The `REMOVED_VARIABLES` old→new rename table | 04.1-07's summary records this as "the single, documented site that still spells the four removed variable names, because a rename cannot be named without naming what was renamed". Removing it sends an owner holding a stale credential off to create one they already have. |
| `scripts/verify-phase4-coverage.mjs` | 211 | A usage string containing this phase's own directory name | The directory is named `04.1-migrate-measurement-from-plausible-to-posthog`. The gate matches the phase's own identity. |
| `src/test/build-output.test.ts` | 891 | The name as a **rejected** value in the approved-host selector table | It is a negative assertion: the name must select nothing. Deleting it deletes the proof. |
| `src/test/measurement.test.ts` | 579 | `['the superseded provider name', 'plausible', 'none']` | Same — the fail-closed resolver must map the superseded name to `none`. This row is the guarantee. |
| `src/test/measurement.test.ts` `src/test/fixtures/posthog-capture-contract.ts` | 478, 133 | Docblock references to this phase's directory path | Same phase-name collision as the verifier's usage string. |

The gate's stated intent — *"No repository instruction names the removed provider"* — is satisfied:
`README.md`, `src/` application code, and `config/` are clean, and this plan cleared the last of
them. The literal grep cannot pass without deleting two negative assertions, a migration aid, and
three references to the phase's own name. Recorded here rather than resolved by deletion.
