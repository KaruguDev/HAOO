### Adjudication of the two code-review blockers

I re-derived both from the codebase rather than accepting the review's account.

**CR-01 — CONFIRMED, and stronger than reported.** The review's grep is correct and I reproduced it, but the decisive evidence is the build I ran myself: a bundle produced with the provider selected, a well-formed `phc_` token and the approved api host contains **zero** vendor code (`$pageview`: 0 occurrences; total 240 kB, consistent with React + app alone). The thirteen `posthog` strings are this project's own refusal reasons, the provider literal, `e.posthog` (the adapter's slot read) and the approved origin. And the repository's own suite states the consequence as an explicit expectation at `src/test/measurement.test.ts:959`: a fully configured measurement config against an empty scope returns `undefined`. The phase ships a measurement stack whose own tests assert it measures nothing in production. Deferred item D4 named 04.1-08 as the plan that must decide the loading strategy *and* restate the two affected build-output invariants in the same commit; 04.1-08's SUMMARY does neither and does not mention D4 at all — its Follow-ups section lists only the four owner gates. Phase 5's roadmap section covers device/accessibility/deployment proof and does not touch SDK loading, so this is **not** deferrable to a later milestone phase.

**CR-02 — CONFIRMED.** `resolveClient` classifies an ambient global as foreign only when it lacks a callable `init` (posthog.ts:129-131, 167); anything else is adopted, handed the project token, and given all ten first-party events. The gate meant to contain that — `lockdownHolds` — inspects the object the untrusted client chose to expose as `instance.config`, and its 33rd check is `typeof merged.before_send === 'function'` (posthog-lockdown.ts:240) while all 32 others compare against literals. A client that returns the configuration object it was handed and swaps its own reducer passes every check and defeats the property chokepoint entirely. The refusal half of the threat model (T-04.1-14, "decide before assign") is genuinely well built and well tested — six hostile shapes, all passing. The accept half grants full trust on one callable property. Because of CR-01 the adopted branch is, in production, reachable *only* by a third party's value. The two findings share one closure: import the SDK, bind to it, refuse any occupied slot, and pin `before_send` by identity.

### Gaps Summary

The engineering discipline in this phase is genuinely high. The lockdown is a closed 33-key object with a `satisfies` build-time partner and a 32-literal runtime readback; the property reducer builds a fresh literal rather than spreading a denylist; the report's positional row reader asserts its column projection before reading; every refusal path is named, swallowed and owner-visible through the real console channel; the deleted-test inventory closed out with zero pending rows; and the human gates are honestly open with `REQUIREMENTS.md` refusing to check a box on code-level closure alone. I probed two central assertions by mutation and both went red, so this is not decorative testing.

What is missing is the one link that makes any of it operative. **No production module loads the PostHog SDK.** The adapter reads a slot nothing fills, so a fully configured deployed build captures zero of the ten events — measured against a real build, and asserted by the repository's own test suite. Every privacy invariant this phase proves is, in production, a statement about unreachable code. Worse, because no legitimate installer exists, the only client the adapter can ever adopt is one a third party put on `window` — and it adopts on the presence of a single callable `init`, then validates the most privacy-load-bearing option by type rather than by identity, so such a client can take the project token, receive the ten bare names, and substitute its own reducer for the chokepoint. The visitor-facing disclosure names PostHog US as the sole processor of that data.

The shipped `README.md` and `COVERAGE.md` state the opposite as settled fact. A reader of this repository's own documentation cannot discover the gap; it is recorded only inside `.planning/deferred-items.md`, as D4, which explicitly assigned the decision to plan 04.1-08. 04.1-08 did not make it and did not carry it forward. For a project whose stated discipline is that a withdrawn guarantee must be named rather than silently dropped, a guarantee that was *added* and does not hold is the most consequential defect here.

Both gaps close in one change, and the change is not free: importing the SDK emits a vendor chunk that will turn `ships the provider-unset bundle with no approved ingestion origin at all` and `keeps the production bundle free of identity and ordered-emission channels` red. D4 already reasons through the two options (scope the origin scan to the entry chunk, or load through a provider-gated dynamic import). Either is a recorded narrowing with a named successor — the shape 04.1-01 established — not a test edit. That reconciliation is the work.

The five residual `plausible` matches are **not** a gap. I read every one in context: four are negative assertions or a rename aid the phase's own contract requires, and three are references to the phase's own directory name. Clause B of Success Criterion 1 is met in substance; the plan-level grep gate is mis-scoped and should be renarrowed to the artifacts it means.

The four open owner gates are **not** gaps either — they are correctly open, correctly documented, and correctly blocking the requirement boxes. But note that gate 3 ("one action, one event") cannot be performed at all until the SDK loading gap is closed: there would be nothing in the live event view to look at.
