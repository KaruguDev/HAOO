### WR-01: A second `createPostHogEventSink` call against the bound module can never confirm the lockdown

**Files modified:** `src/measurement/posthog.ts`, `src/test/fixtures/posthog-capture-contract.ts`, `src/test/measurement.test.ts`
**Commit:** `4ba7e8c`
**Status:** fixed — behavioural change, worth a human read of the gate's POSITION

**Applied fix.** Made the module's own behaviour correct under re-entry rather than
documenting the precondition, as directed. A module-scoped `WeakMap<PostHogClient, …>`
records what has already been established — token, api host, a COPY of the event allowlist,
and the sink that initialization produced — and is consulted between the client gate and
`POSTHOG_LOCKDOWN(...)`:

- Same client + same configuration → the established sink is returned. The vendor is never
  re-entered, so there is no second merged configuration for the identity readback to
  disagree with, and the false `posthog:unconfirmed-lockdown-readback` cannot be reached.
- Same client + DIFFERENT configuration → a new named refusal,
  `POSTHOG_REFUSAL.reconfiguration` (`posthog:refused-client-reconfiguration`). At the
  pinned SDK the second `init` is a no-op that keeps the first configuration, so honouring
  the second call would mean delivering events under a project key and an allowlist the
  caller did not ask for. Refusing says the one thing this module genuinely cannot do, in
  its own words, instead of mis-saying it as the privacy alarm.

**The identity check was not touched.** `merged.before_send === expected.beforeSend`
(`posthog-lockdown.ts:290`) is byte-identical, `POSTHOG_LOCKDOWN` still mints a fresh
closure per call, and G-04.1-2 keeps its teeth. The memo cannot launder anything: an entry
is written only on the far side of a real `init` and a CONFIRMED readback, and it is keyed
by client identity.

**Gate ordering** is the safety property and is recorded in the function's docblock: the
re-entry gate sits AFTER every gate that classifies a client (so an occupied ambient slot is
still `foreignClient`, and a half-empty configuration is still `unconfigured`) and BEFORE
anything is sent to one. A `WeakMap` rather than a single slot, because a single slot would
silently drop the first client's establishment as soon as a second client appeared —
reopening this same defect for the first.

**Verification.** Re-read; `npm run typecheck` clean; 251/251 in `measurement.test.ts`;
full suite green. **Mutation-probed both directions**, which is the part that matters here:

- Removing the re-entry gate turned **6 cases red** (5 unit + 1 journey row) — the gate has
  teeth.
- `still refuses, on every call, when the lockdown genuinely does not hold` **passes in both
  states**. It asserts `[lockdown, lockdown]` against a client whose merged config resolves
  `autocapture` wrong: nothing is established by a refused call, so a broken lockdown still
  fires the alarm on the second call as on the first. The alarm was fixed, not silenced.

New coverage (9 cases): established-sink identity + one `init` + no reason; second sink still
delivering one payload per allowlisted name with the console SILENT; the genuinely-broken
direction above; three reconfiguration rows (project key, ingestion origin, event allowlist);
an ordering probe (an emptied configuration still refuses `unconfigured`, so a repeat call is
not a way past the earlier gates); a per-client isolation case; and one row in the full-journey
refusal table so the new reason is proven not to cost the visitor a journey.

New fixture `createLoadedOncePostHogVendorClient` models the vendor's `__loaded`
short-circuit, transcribed from the installed `dist/module.js`. Against the re-merging
sibling fixture every one of these cases would pass whether or not the module was fixed —
which is exactly why the defect was invisible to the existing suite.

### WR-02: The workflow credential gate only catches credentials whose *variable name* contains a forbidden token

**Files modified:** `src/test/build-output.test.ts`, `.github/workflows/deploy.yml` (comment only)
**Commit:** `54b8dc1`

**Applied fix.** The gate now reads what a browser-prefixed variable is ASSIGNED, not only
what it is called. `browserPrefixedAssignments()` parses every `VITE_*: value` line out of
the workflow text, and each value must satisfy two rules: not drawn from the secrets context
(`SECRETS_CONTEXT`), and exactly one `${{ vars.NAME }}` expression
(`REPOSITORY_VARIABLE_EXPRESSION`). The existing name-side assertions are untouched — they
were never wrong, only partial.

The positive form is deliberate. A `secrets.` denylist alone would still pass a literal
`VITE_HAOO_ANALYTICS_KEY: phx_liveKey` (the same leak with the expression removed) and
`${{ github.event.* }}` (attacker-controlled text inlined into a shipped bundle). `vars.*`
is the only source whose contents are world-readable by construction — which is the property
`dist` gives everything it carries.

**Shell-injection surface:** none added. The check is a line-anchored regex over the file's
own text, in-process. Nothing is executed, interpolated into a shell, or passed to a
process — building a command line out of repository content inside the gate that exists to
keep credentials out of a build would have been the wrong trade.

**Vacuity probe:** the reviewer's own experiment, made executable —
`catches a report credential smuggled under an unforbidden browser-prefixed name` builds a
mutant from the REAL workflow (not a fixture, which would keep passing after the file's
shape moved) with `VITE_HAOO_ANALYTICS_KEY: ${{ secrets.POSTHOG_QUERY_API_KEY }}` added, and
asserts BOTH halves: that the two name-side regexes stay blind to it, and that the value-side
rule names it. Non-vacuity inside the gate itself is asserted before the loop, and the exact
browser-variable roster is asserted after it.

**Verification.** Re-read; lint + typecheck clean; 40/40 in `build-output.test.ts`.
**Mutation-probed against the real file**: adding that exact line to `.github/workflows/deploy.yml`
turns the gate red with `VITE_HAOO_ANALYTICS_KEY carries a secrets-context value. Vite inlines
every VITE_* value into a world-readable bundle…`. Assertion order was adjusted after the
first probe so the failure names the credential rather than reporting a list-length mismatch.
`deploy.yml` was restored byte-identical apart from the added comment; the three
`VITE_HAOO_*` Build variables are untouched (`git diff` over the whole range shows no changed
`VITE_` assignment).
