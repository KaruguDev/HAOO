### WR-05: `defaults: 'unset'` does not pin the date-gated default bundle

**Files modified:** `src/measurement/posthog-lockdown.ts`, `src/test/measurement.test.ts`
**Commit:** `b6e3576`
**Applied fix:** Took the review's primary option. The claim was verified against
`node_modules/posthog-js/dist/module.js` rather than assumed — `'unset' >= '2026-01-30'` is `true`
and `'2025-11-30' > 'unset'` is `false`, so the sentinel sorts above every date literal and selects
the newest branch of every gate except `session_recording`, which special-cases the literal. The doc
comment now states what the option actually does, and why there is no live impact today (all three
date-gated keys carrying a privacy decision are locked and read back).

The standing rule is **executable, not advisory**: a new suite extracts every date-gated key out of
the installed bundle and fails on any key this project has neither locked nor explicitly
acknowledged, naming it. Nine such keys exist at this version; six are unlocked and are now named
with the value `'unset'` actually selects. Probe: dropping one acknowledgement reports that key by
name.

Real pinning — passing an early date literal instead of `'unset'` — was **deliberately not taken**.
It is a behavioural decision about which vendor default set this project adopts, not a comment
correction, and choosing the pin date has non-obvious per-gate consequences (`'2025-05-24'` does not
select the oldest branch of the `capture_pageview` gate). That belongs to an owner decision.

## Skipped Issues

### CR-01: The PostHog SDK is never loaded, so no event can ever be captured in a deployed build

**File:** `src/measurement/posthog.ts:148-170`, `src/measurement/posthog-lockdown.ts:1`, `package.json:22`
**Reason:** skipped — enabling delivery is a deferred architectural decision with a named successor,
not a mechanical fix, and the review itself offers the alternative that was taken instead.

The gap is real and the review's diagnosis was verified independently. It is recorded as deferred
item **D4** with the loading strategy explicitly left to "whichever plan turns ingestion on for
real", and `04.1-08` gates the live one-action-one-event confirmation behind an owner action. Three
things put it outside a fixer's authority:

1. **It is not a one-line import.** Emitting the vendor chunk turns two currently-green,
   deliberately-established, mutation-proven bundle invariants red at once — that a provider-unset
   bundle carries no approved ingestion origin at all, and that the production bundle carries no
   browser-storage or identifier channels. Both must be *restated* in the same commit, and choosing
   between the two recorded candidate narrowings (scoping the origin scan to the entry chunk, versus
   a provider-gated dynamic import whose chunk is only emitted for a selected build) is a design
   decision, not a repair.
2. **Turning on real ingestion is owner-gated.** This is a privacy migration whose activation
   checklist includes owner-performed project settings that no code can assert. Enabling delivery
   autonomously would bypass that gate.
3. The review states the alternative explicitly: *"If enabling this is genuinely out of scope for
   04.1, the phase must not ship `README.md` and `COVERAGE.md` asserting the bundled behaviour as
   fact (see WR-01)."*

**What was done instead:** WR-01 (`85c6fab`) makes the shipped documents tell the truth — the README
now states in its own section that zero events are delivered and why a report of zeros is expected —
and adds a bidirectional gate so the documents and the code cannot diverge again. The moment a
production module loads the SDK, that gate fails and names the module, forcing the README to be
rewritten in the same commit. The finding is therefore **disclosed and fenced, not closed.**

### CR-02: The adapter adopts an arbitrary third-party `window.posthog`

**File:** `src/measurement/posthog.ts:148-170`, `src/measurement/posthog.ts:231-278`, `src/measurement/posthog-lockdown.ts:240`
**Reason:** skipped — **partially closed**; the remaining half is structurally blocked on CR-01.

The finding has two halves and they were not equally tractable:

- **Closed (commit `33deb5a`, filed under WR-02):** `before_send` is now pinned by identity rather
  than by `typeof`. The review's specific escape route — *"substituting its own reducer defeats the
  property chokepoint entirely"* while still passing the readback — is refused.
- **Not closed:** *"Do not adopt. Bind the client to the imported module and refuse any occupied
  slot outright."* This presupposes CR-01. There is no imported module to bind to, so refusing every
  occupied slot would leave `adapters.client` — a test-only injection seam — as the sole path to a
  client, permanently. That is not a hardening of the design; it is a different design, and it
  **prejudges the loading strategy D4 reserves for a later plan**: if that plan chooses the vendor's
  standard snippet, which assigns `window.posthog`, an unconditional ambient refusal breaks it
  before it is written. It would also require refactoring every ambient-scope test in
  `measurement.test.ts` onto the `adapters.client` seam, which would delete the coverage of the
  refusal ordering the review praises as *"correct and well tested"*.

**Residual exposure, stated plainly:** an ambient client that exposes a callable `init` and echoes
back the configuration object it was handed still passes the readback, and still sees the public
project key and the ten bare event names. Identity-pinning `before_send` does not stop that,
because such a client controls `capture` and never runs the reducer at all. In production today the
branch is unreachable by anything legitimate — which is precisely the review's point, and precisely
why it must be resolved by the same plan that resolves CR-01, in the same commit that decides how
the client legitimately arrives.
