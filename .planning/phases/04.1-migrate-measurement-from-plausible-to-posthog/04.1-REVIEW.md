# Phase 04.1: Code Review Report

## Summary

Verification baseline established before reviewing: `npm run typecheck` passes, `npm run lint` passes, `npx vitest run` passes 639/639. None of the findings below are caught by that gate — which is itself part of the problem.

The reporting half of this migration (`src/reporting/*`, `scripts/generate-haoo-report.mjs`) is well built. The credential genuinely travels only in an `Authorization` header, `renderReport` escapes every interpolated value including `projectScope`, `parseGoalCounts` asserts the `columns` projection before reading positional rows, `validateEchoedQuery` compares the echoed SQL byte-for-byte, and the write-on-success temp-file/rename dance is correct including the ownership rule on the cross-invocation mutex. I found two divergences there, both narrow.

The browser half does not do what the phase claims. **Nothing in the repository imports `posthog-js` as a value.** The only reference is `import type` in `posthog-lockdown.ts`, which is fully erased at build time. The adapter resolves its client exclusively from the ambient `window.posthog` slot, which no shipped module ever assigns. In a fully configured production build the adapter therefore refuses at the `absentClient` gate, returns `undefined`, and **zero of the ten allowlisted events ever leave the page**. Every one of the phase's privacy invariants about what a captured event carries is currently vacuous, and the second-order consequence is worse: because no legitimate installer exists, the only client that can ever be adopted is one a third party put there — and the adapter will adopt it, hand it the project token, and route all ten first-party events through it.

This gap is recorded in `04.1-04-SUMMARY.md` as deferred item D4, so it is known. It is still reported here as a BLOCKER because the shipped `README.md` and `COVERAGE.md` state the opposite as settled fact, and because the "exactly ten bare event names leave the page" invariant this review was asked to verify is not true of this code.

The remaining warnings cluster on assertion strength: several bundle-level security prohibitions pass vacuously when `dist/assets` is absent, the coverage-audit script is never executed by any automated gate, and `lockdownHolds` accepts any function at all as `before_send`.

## Critical Issues

### CR-01: The PostHog SDK is never loaded, so no event can ever be captured in a deployed build

**File:** `src/measurement/posthog.ts:148-170`, `src/measurement/posthog-lockdown.ts:1`, `package.json:22`
**Issue:**
`posthog-js@1.425.1` is declared as a production dependency, but the only reference to it anywhere in the tree is a type-only import:

```
$ grep -rn "posthog-js" src/ config/ scripts/ vite.config.ts
src/measurement/posthog-lockdown.ts:1:import type { CaptureResult, PostHogConfig } from 'posthog-js';
```

`import type` is erased by TypeScript, so the SDK is never bundled. Confirmed against the built artifact: `dist/assets/*.js` contains ten occurrences of the string `posthog`, and all of them are this project's own refusal reasons (`posthog:absent-provider-client`, `posthog:unconfirmed-lockdown-readback`, …) plus the `'posthog'` provider literal. No vendor code is present.

`resolveClient` reads the client only from `scope.posthog` (`window.posthog`) and nothing in `src/` ever assigns it — the sole assignment in the repository is `src/test/fixtures/posthog-capture-contract.ts:185`, a test fixture. So on a build with `VITE_HAOO_MEASUREMENT_PROVIDER=posthog`, a valid `phc_` token and an approved api host, the sequence is:

1. `createPostHogEventSink` passes the provider and configuration gates.
2. `resolveClient` reads `window.posthog` → `undefined` → returns `{ reason: POSTHOG_REFUSAL.absentClient }`.
3. `signalRefusal` writes `posthog:absent-provider-client` to `console.warn` on **every page load**.
4. The sink is `undefined`; `track()` calls `eventSink?.(event)` on a nothing.

Consequences: none of the ten allowlisted events is ever sent; the owner report (`npm run report:haoo`) will correctly return zeros forever and — per the phase's own D-05 reasoning — a permanently refusing provider is indistinguishable from a dead funnel to anyone not watching the browser console; `posthog-js` is an unused ~1MB production dependency; and every privacy invariant this review was asked to verify about captured payloads is unreachable code.

The entire lockdown, readback and `before_send` chokepoint — the bulk of the phase's privacy engineering — is dead in production.

**Fix:** Import the SDK as a value and install it into the slot the adapter reads, before `resolveClient` runs. Keep the decide-before-assign rule by refusing when the slot is already occupied by something foreign (see CR-02):

```ts
// src/measurement/posthog.ts
import posthog from 'posthog-js';

// ...inside createPostHogEventSink, replacing the ambient-only resolution:
const resolvedClient = adapters.client !== undefined
  ? { client: adapters.client }
  : resolveClient(scope, adapters, posthog); // installs the pinned SDK when the slot is empty
```

Note this will turn `src/test/build-output.test.ts` red — the vendor chunk contains `localStorage`, `sessionStorage` and identifier tokens (recorded as deferred item D1, with the pre-agreed handling: relocate those patterns to the production-source scan, since a minified vendor artifact is a claim about the vendor, not this repository). That reconciliation is the work; it is not a reason to ship a measurement stack that cannot measure.

If enabling this is genuinely out of scope for 04.1, the phase must not ship `README.md` and `COVERAGE.md` asserting the bundled behaviour as fact (see WR-01).

### CR-02: The adapter adopts an arbitrary third-party `window.posthog` and hands it the project token and every captured event

**File:** `src/measurement/posthog.ts:148-170` and `src/measurement/posthog.ts:231-278`; `src/measurement/posthog-lockdown.ts:240`
**Issue:**
`resolveClient` classifies a pre-existing ambient global as *foreign* only when it lacks a callable `init`. Anything exposing `init` as a function is **adopted**: this project then calls `foreign.init(providerConfig.token, POSTHOG_LOCKDOWN(...))` and, if the readback passes, routes all ten HAOO events into `foreign.capture(...)`.

Because of CR-01 nothing legitimate ever occupies that slot, so in production the adopted-client branch is reachable *only* by a value some other party put on `window` — a browser extension, a tag manager, an injected snippet. The gate that is supposed to stop this (`lockdownHolds`) cannot: it inspects the object the untrusted client chose to expose as `instance.config`. A hostile client that simply returns the configuration object it was handed passes all 32 value checks, and the 33rd check is `typeof merged.before_send === 'function'` — it never verifies the function is *this project's* `before_send`. Substituting its own reducer defeats the property chokepoint entirely, at which point the adopted client sees:

- the public project key,
- the ten bare event names in real time,
- whatever properties it chooses to attach, since the reduction it was supposed to apply is its own.

The visitor-facing disclosure rendered by `MeasurementDisclosure.tsx` names PostHog US as the sole processor of this data. That statement is not true of an adopted global.

The phase's threat model records this exact vector (T-04.1-14, "decide before assign") and mitigates only half of it: the refusal path is correct and well tested (`measurement.test.ts:901-971` — non-callable value, frozen object, string, number, throwing getter, throwing slot read), but the accept path grants full trust on the presence of a single callable property.

**Fix:** Do not adopt. Bind the client to the imported module and refuse any occupied slot outright, and pin `before_send` by identity rather than by type:

```ts
// posthog.ts — never adopt an ambient value
if (scope.posthog !== undefined && scope.posthog !== posthog) {
  return { reason: POSTHOG_REFUSAL.foreignClient };
}

// posthog.ts — retain the object that was sent so the readback can prove identity
const lockdown = POSTHOG_LOCKDOWN(providerConfig.apiHost, providerConfig.token, config.events);
instance = resolvedClient.client.init(providerConfig.token, lockdown);
confirmed = lockdownHolds(readProperty(instance, 'config'), {
  apiHost: providerConfig.apiHost,
  token: providerConfig.token,
  beforeSend: lockdown.before_send,   // new expectation member
});

// posthog-lockdown.ts — identity, not typeof
merged.before_send === expected.beforeSend
```

## Warnings

### WR-01: `README.md` and `COVERAGE.md` assert bundled-SDK behaviour the code does not have

**File:** `README.md:107-124`; `scripts/verify-phase4-coverage.mjs:5`
**Issue:** The README states "The SDK is now a pinned bundled dependency, so that bundle-level origin guarantee is **withdrawn** — the built bundle necessarily carries the vendor's own code and its own default host," and "The sink sends exactly one bare allowlisted event name per explicit action." Neither is true of the shipped artifact (CR-01): the bundle carries no vendor code, and the sink sends nothing. `verify-phase4-coverage.mjs` likewise hardcodes the required table heading `'PostHog — browser SDK (posthog-js, bundled)'` with `'bundled `posthog.init(token, config)` with an explicit lockdown object'` marked `INTEGRATE`, so the audit script asserts the same untrue fact. A reader of these documents cannot discover the gap; it is recorded only inside `.planning/`.

This is the most consequential class of defect for a project whose stated discipline is that a withdrawn guarantee must be named rather than silently dropped — here a guarantee was *added* that does not hold.

**Fix:** Either implement CR-01, or amend the README's "The analytics code is bundled, not fetched" section and the COVERAGE row to state plainly that the SDK is pinned but not yet loaded, that no event is currently delivered, and which plan closes it. Add an assertion that fails when the two diverge, e.g. a test that greps `src/` for a value import of `posthog-js` and requires it whenever the README makes the bundled claim.

### WR-02: `lockdownHolds` validates `before_send` by type only, so the property chokepoint is never proven

**File:** `src/measurement/posthog-lockdown.ts:240`
**Issue:** Every other locked key is compared against an explicit literal. `before_send` — the single most privacy-load-bearing option, described in this file as "the property chokepoint" and "the second, independent layer under D-04" — is checked as `typeof merged.before_send === 'function'`. Any function passes. The per-key hostile table in `measurement.test.ts:866` only proves that a *non-function* value is refused, so the gap is invisible to the suite. The lockdown object is discarded at the call site (`posthog.ts:233-236` constructs it inline), so identity is not currently available to the predicate.

**Fix:** As shown in CR-02: retain the object passed to `init`, add `beforeSend` to `PostHogLockdownExpectation`, and assert `merged.before_send === expected.beforeSend`. Add a test row that substitutes a different function and expects `POSTHOG_REFUSAL.lockdown`.

### WR-03: `POSTHOG_PROJECT_ID` is interpolated unvalidated into the credentialed request URL

**File:** `scripts/generate-haoo-report.mjs:79`, `scripts/generate-haoo-report.mjs:133`
**Issue:**

```js
const projectId = process.env.POSTHOG_PROJECT_ID ?? '';
// ...
endpoint: `${QUERY_API_ORIGIN}${QUERY_API_PATH_PREFIX}${projectId}${QUERY_API_PATH_SUFFIX}`,
```

The only check is `projectId.trim() !== ''`. A value containing `/`, `..`, `?` or `#` silently reshapes the URL the API key is sent to — `POSTHOG_PROJECT_ID='1/../../users/@me'` sends the credential to a different endpoint on the same host. `README.md:149-151` explicitly promises "It is the numeric project id … must not be entered as a URL with a scheme or path", but nothing enforces it. This is a striking inconsistency with the rest of the phase: `resolvePostHogToken` and `resolvePostHogApiHost` reject on every deviation and are exhaustively tested, while the one value that shapes a *credentialed* request is unvalidated. The same unvalidated string also becomes the report's `projectScope` label (it is HTML-escaped, so there is no XSS, but it is rendered).

**Fix:**

```js
const PROJECT_ID_SHAPE = /^[0-9]+$/;
const projectId = (process.env.POSTHOG_PROJECT_ID ?? '').trim();
if (projectId !== '' && !PROJECT_ID_SHAPE.test(projectId)) {
  writeTerminalError(
    'POSTHOG_PROJECT_ID must be the numeric project id, with no scheme, path, or query.',
    ERROR_STATE_SENTENCE,
  );
  process.exitCode = 1;
}
```

Apply the check before `generateHaooReport` is reached, alongside the existing missing/stale-variable branches.

### WR-04: `parseFirstRecordedDay` reads a positional row without the `columns` equality assertion every other parser makes

**File:** `src/reporting/generate.ts:355-372`
**Issue:** `parseGoalCounts` (`stats-response.ts:40-45`) asserts `columns` equals `['event','occurrences']` *before* the row loop, with a doc comment explaining that "a reordered projection would swap them and parse cleanly into wrong numbers". `parseFirstRecordedDay` performs exactly the same kind of positional read — `body.results[0][0]` — with no `columns` check at all. `COVERAGE.md` lists "response `columns` equality assertion" as an `INTEGRATE` capability of the Query API surface, so this is a divergence from the phase's own recorded contract. The risk is bounded (the row-length-1 and `ISO_DAY` checks catch most shapes), but a response projecting a different single ISO-shaped column would be accepted as the first recorded day and printed into the all-time heading as a claim.

**Fix:**

```ts
const HOGQL_FIRST_DAY_COLUMNS = ['first_day'] as const;
// inside parseFirstRecordedDay, before reading results:
const columns = body.columns;
if (!Array.isArray(columns) || columns.length !== 1
  || columns[0] !== HOGQL_FIRST_DAY_COLUMNS[0]) {
  return { ok: false, reason: 'invalid' };
}
```

The CLI fetch fixture already returns `columns: ['first_day']` (`haoo-report-cli-fetch-preload.mjs:131`), so no fixture change is needed.

### WR-05: `defaults: 'unset'` does not pin the date-gated default bundle in posthog-js@1.425.1

**File:** `src/measurement/posthog-lockdown.ts:29-30`, `src/measurement/posthog-lockdown.ts:75`
**Issue:** The doc comment claims `defaults: 'unset'` "pins behaviour to the values written here rather than to the vendor's date-gated default bundle, which moves inside its own major line." The vendor's implementation only partially honours that. In `node_modules/posthog-js/dist/module.js` the date gates are plain **string comparisons** against the `defaults` value, and only `session_recording` special-cases the literal `'unset'`:

```js
Nl = t => t && "unset" !== t ? { /* date-gated */ } : {}          // honours 'unset'
// but:
rageclick:                    !t || "2025-11-30" > t || { content_ignorelist: true }
capture_pageview:             !t || "2025-05-24" > t || "history_change"
internal_or_test_user_hostname: t && t >= "2026-01-30" ? /^(localhost|127\.0\.0\.1)$/ : void 0
external_scripts_inject_target: t && t >= "2026-01-30" ? "head" : "body"
```

`'unset' >= '2026-01-30'` is `true` and `'2025-11-30' > 'unset'` is `false`, so `'unset'` sorts *above every date literal* and selects the **newest** branch, not "no defaults". Today there is no live impact — `rageclick`, `capture_pageview` and `internal_or_test_user_hostname` are each explicitly overridden and read back — but the stated guarantee is false, and any date-gated default the vendor adds in future that is not one of the 33 keys in the lockdown will be silently opted into at its newest value rather than pinned. That is precisely the drift this option was chosen to prevent.

**Fix:** Correct the comment to state what `defaults` actually does at this version, and add the standing rule that a version bump requires re-reading the SDK's default builder for newly date-gated keys. If pinning is genuinely wanted, pass an explicit early date literal (e.g. `defaults: '2025-05-24'`) and assert it in `lockdownHolds`, so the comparisons resolve to the oldest branch deterministically.

### WR-06: The bundle-level security prohibitions pass vacuously when `dist/assets` is absent

**File:** `src/test/build-output.test.ts:288-292`, `src/test/build-output.test.ts:714-731`, `src/test/build-output.test.ts:783-796`, `src/test/build-output.test.ts:955-963`
**Issue:** `builtBundleText()` builds on `listFiles()`, which returns `[]` for a missing directory, so it returns the empty string when `dist/` has not been built. Every prohibition expressed as `expect(bundle).not.toMatch(...)` then passes against `''`:

- `ships the unset provider bundle without competitor analytics, property, or credential seams` — the `POSTHOG_QUERY_API_KEY` / `Authorization` / `Bearer` / `/api/projects/:id/query` credential scan.
- `keeps the production bundle free of identity and ordered-emission channels`.
- `ships the provider-unset bundle with no approved ingestion origin at all`.

The freshness case (`requires every production build output to exist`) does fail separately, but it is a *different* test: the security assertions themselves report green, so a reader scanning results sees the credential-boundary contract passing on a build that was never produced. CI happens to run `npm run build` first, and `npm test` chains it, but `npm run test:unit` alone (documented and used) does not. The same vacuity affects `readText()`, which returns `''` for a missing path — `leaves no superseded approved-script-source module or constant behind` scans `readText(vite.config.ts)` and `readText(src/vite-env.d.ts)`, both of which would pass on a rename.

The narrowed-boundary case at line 632 already demonstrates the right guard (`expect(source, relativePath).not.toBe('')`); it is simply not applied here.

**Fix:**

```ts
function builtBundleText() {
  const files = listFiles(resolve(DIST, 'assets')).filter((f) => f.endsWith('.js'));
  if (files.length === 0) {
    throw new Error('No built bundle to scan. Run npm run build before asserting against dist/assets.');
  }
  return files.map((file) => readFileSync(file, 'utf8')).join('\n');
}
```

and add `expect(text, path).not.toBe('')` before every `readText(...).not.toMatch(...)` prohibition.

### WR-07: The Phase 4 coverage audit is never executed by any automated gate

**File:** `scripts/verify-phase4-coverage.mjs:131`, `scripts/verify-phase4-coverage.mjs:208-225`; `package.json:6-16`; `.github/workflows/deploy.yml`

### WR-08: `heading in REQUIRED_TABLES` matches inherited `Object.prototype` keys

**File:** `scripts/verify-phase4-coverage.mjs:111`
**Issue:** `REQUIRED_TABLES` is a plain object literal, so the `in` operator walks its prototype. A `COVERAGE.md` section headed `## constructor`, `## toString`, `## valueOf`, `## hasOwnProperty` etc. satisfies `heading in REQUIRED_TABLES` and a malformed row inside it aborts the whole audit with `constructor: malformed row with 2 cells: …` — an error naming a table that does not exist. The reverse also holds: `tables.get(heading)` and `Object.entries(REQUIRED_TABLES)` use own-key semantics, so the two halves of the same function disagree about what a required table is. Same class of issue as the array-smuggling guard `isPlainObject` exists to prevent in `src/reporting/untrusted.ts`, applied inconsistently.

Relatedly, three of the nine `boundaryChecks` are name-presence only (``/`POSTHOG_QUERY_API_KEY`/``, ``/`POSTHOG_PROJECT_ID`/``, `/provider selector\s+remains unset/iu`) — the same weakness the file's own comments call out and tighten for four *other* rows ("a bare `/deferred/` passed on any occurrence of the word anywhere in the section, including one saying the opposite"). A sentence saying `POSTHOG_QUERY_API_KEY` may be published would pass.

**Fix:**

```js
if (Object.hasOwn(REQUIRED_TABLES, heading)) {
  throw new Error(`${heading}: malformed row with ${cells.length} cells: ${line}`);
}
```

and tighten the three name-presence boundary checks to pin the sentence they mean to assert, as the other six already do.

### WR-09: The provider-selected probe build is not portable and inherits the developer's environment

**File:** `src/test/build-output.test.ts:930-955`
**Issue:** Two problems in one case:

1. `spawnSync('npx', [...], { cwd: ROOT })` without `shell: true` fails with `ENOENT` on Windows, where the executable is `npx.cmd`. The failure surfaces as `build.status` being `null`, so `expect(build.status).toBe(0)` fails with an opaque message rather than naming the cause. This repository explicitly supports Windows — `directoryOf` in `src/reporting/generate.ts:135-160` carries 20 lines of doc comment about drive designators and UNC roots, and `.planning/WINDOWS.md` is tracked — so the platform is in scope.
2. `env: { ...process.env, VITE_HAOO_MEASUREMENT_PROVIDER: 'posthog' }` passes the developer's entire environment through. A shell that exports `VITE_HAOO_POSTHOG_TOKEN` or `VITE_HAOO_POSTHOG_API_HOST` (exactly the shell an owner performing the 04.1-08 activation would have) bakes those real values into `dist-approved-host-probe/`. The directory is removed in `finally`, but an uncatchable termination leaves a bundle carrying live configuration on disk — the same failure shape the report generator's temp-file reasoning is careful about.

**Fix:**

```ts
const build = spawnSync(process.platform === 'win32' ? 'npx.cmd' : 'npx', [...], {
  cwd: ROOT,
  encoding: 'utf8',
  env: {
    ...process.env,
    VITE_HAOO_MEASUREMENT_PROVIDER: 'posthog',
    VITE_HAOO_POSTHOG_TOKEN: '',
    VITE_HAOO_POSTHOG_API_HOST: '',
  },
});
```

### WR-10: The vendor fixture's "documented defaults" omit nine of the locked keys, weakening the readback premise

**File:** `src/test/fixtures/posthog-capture-contract.ts:67-89`
**Issue:** The fixture's doc comment states the premise precisely — "A stub that started from the locked-down values would make a readback assertion vacuous … Starting from the defaults means every locked value has to be overcome by a real `init` argument." But `VENDOR_DOCUMENTED_DEFAULTS` carries 20 keys while `lockdownHolds` asserts 33. Nine locked keys have no default at all in the fixture: `ui_host`, `defaults`, `internal_or_test_user_hostname`, `disable_scroll_properties`, `advanced_disable_feature_flags`, `advanced_disable_toolbar_metrics`, `opt_in_site_apps`, `disableDeviceModel`, `custom_campaign_params`. For those, `{...defaults, ...config}` yields the adapter's own value and the assertion proves the object equals itself — the exact vacuity the comment forbids. `internal_or_test_user_hostname` is the one that matters most: the vendor's real default at this version is a regex (see WR-05), and it is documented in `posthog-lockdown.ts:30` as "explicit because a non-null value enables person processing".

Mitigation: the per-key hostile table (`measurement.test.ts:866-885`) does force a wrong resolved value for every key, so a broken readback is still caught. The residual gap is narrower — an adapter that *omitted* one of these nine keys entirely would still be caught by `lockdownHolds` returning false on `undefined`. So this is a fidelity defect in the fixture's stated premise rather than an escape route; it should be closed because the premise is what future readers will trust.

**Fix:** Add the nine missing keys to `VENDOR_DOCUMENTED_DEFAULTS` at their real vendor values (`internal_or_test_user_hostname: /^(localhost|127\.0\.0\.1)$/`, `opt_in_site_apps: false`, `disableDeviceModel: false`, `disable_scroll_properties: false`, `advanced_disable_feature_flags: false`, `advanced_disable_toolbar_metrics: false`, `ui_host: null`, `defaults: undefined`, `custom_campaign_params: []`), and add an assertion that every key in `LOCKED_KEYS` appears in the fixture's default map, so a key added to the lockdown without a corresponding default fails loudly.
