## Summary

The three things this round was judged on hold up under direct reading:

- **`resolveClient` refusal completeness is genuine.** `src/measurement/posthog.ts:257-283` reads the ambient slot exactly once inside `try`, treats an unclassifiable read as `foreignClient`, and refuses every defined non-null value before any structural inspection. There is no write, no wrap, no `delete`, and no second read on any path, so "left byte-identical" is a property of the control flow rather than of the assertions. Prototype-inherited values and throwing getters both land on the refusal branch; the only remaining reachable clients are `boundPostHogClient()` and an explicitly injected `adapters.client`, which no production caller supplies (`src/App.tsx:657` renders `ProductPage` with no adapters).
- **The `before_send` check is real identity.** `src/measurement/posthog-lockdown.ts:290` compares `merged.before_send === expected.beforeSend`, fed from the retained lockdown object at `src/measurement/posthog.ts:374`. `POSTHOG_LOCKDOWN` is a factory minting a fresh closure per call, so no substituted callable can satisfy it, and the `typeof` guard ahead of it prevents a non-function expectation from short-circuiting.
- **The deploy workflow exposes no secret.** All four Build values come from `vars.*`, nothing is interpolated into a `run:` script, and neither report credential appears anywhere in `deploy.yml`. The `phc_` token being a repository variable is out of scope per the review brief and is not reported.

What the round did not get right is concentrated in the gates and the prose around them. One latent correctness defect (WR-01) follows directly from combining the module-singleton binding of 04.1-09 with the identity readback of `33deb5a`, and neither plan noticed it. Two gates claim more than they check (WR-02, WR-05), one gate now pins a sentence the code itself calls false (WR-03), and three threats the new code cites do not exist in the phase threat register (WR-04).

No Critical findings. No secret, injection, or data-loss defect was found in the reviewed diff.

## Warnings

### WR-01: A second `createPostHogEventSink` call against the bound module can never confirm the lockdown

**File:** `src/measurement/posthog.ts:353-389`, with `src/measurement/posthog-lockdown.ts:128` and `:290`

**Issue:** `POSTHOG_LOCKDOWN` is a factory: every call mints a **new** `before_send` closure (`posthog-lockdown.ts:128`). `boundPostHogClient()` returns the `posthog-js` module **singleton**. At the pinned 1.425.1 the vendor's initializer short-circuits on re-entry — `node_modules/posthog-js/dist/module.js` contains `if(this.__loaded)return …,this;this.__loaded=!0,this.config=…` — so a second `init()` returns the instance **without applying the new configuration**.

The consequence: on any second call, `readProperty(instance,'config').before_send` is still the **first** call's closure, while `expected.beforeSend` is the **second** call's fresh closure. The identity comparison at `posthog-lockdown.ts:290` therefore fails, `lockdownHolds` returns `false`, and the adapter emits `POSTHOG_REFUSAL.lockdown` (`posthog:unconfirmed-lockdown-readback`) and returns no sink — for the rest of the page's life.

That refusal reason is the phase's loudest alarm: per D-05 and `04.1-SECURITY.md` it means "the privacy lockdown could not be confirmed". Here it would be a **false** alarm produced by this project's own re-entry, sending an owner to hunt a privacy regression that does not exist, while measurement is silently dead.

Reachability today is narrow but not closed: `src/measurement/index.ts:303-305` guards with an `initialized` flag and `src/pages/ProductPage.tsx:74-78` guards with a ref, and `App.tsx:657` passes no `measurementAdapters`, so exactly one facade is built per page load. The defect surfaces the moment a second facade exists — a remount, a second product page, a router, or a caller passing an inline `measurementAdapters` object (which makes the `useMemo` at `ProductPage.tsx:53-55` unstable). Nothing in the suite covers a second initialization: every test either injects a fresh fixture client or spies on `init`.

**Fix:** make repeat initialization idempotent rather than self-refuting. Memoize the resolved sink for a given client + configuration, so the second call returns the first sink instead of re-initializing:

```ts
// module scope in src/measurement/posthog.ts
let established: {
  readonly client: PostHogClient;
  readonly token: string;
  readonly apiHost: string;
  readonly sink: (event: string) => void;
} | null = null;

// after the client gate, before POSTHOG_LOCKDOWN(...):
if (
  established !== null
  && established.client === resolvedClient.client
  && established.token === providerConfig.token
  && established.apiHost === providerConfig.apiHost
) {
  return established.sink as (event: EventName) => void;
}
```

…and assign `established` alongside the returned sink. Add a regression case that calls `createPostHogEventSink` twice against the same client and asserts a working sink and **no** `POSTHOG_REFUSAL.lockdown` signal on the second call.

### WR-02: The workflow credential gate only catches credentials whose *variable name* contains a forbidden token

**File:** `src/test/build-output.test.ts:994-1005` (case at `:962`), with `.github/workflows/deploy.yml:69-74`

**Issue:** The case is named "keeps **every** report credential out of the deploy workflow Build environment" and `deploy.yml:71-74` says the test "asserts their absence". Both assertions inside it key on the credential's **name**: `not.toMatch(/VITE[A-Z0-9_]*_POSTHOG_QUERY_API_KEY|VITE_POSTHOG_QUERY_API_KEY/)` and a line-anchored `^ *(?:VITE_[A-Z0-9_]*)?POSTHOG_QUERY_API_KEY: ` assignment count. Neither looks at what a browser-prefixed variable is **assigned**.

Verified by applying the two exact regexes to a mutated copy of the real workflow with this line added to the Build `env` block:

```yaml
VITE_HAOO_ANALYTICS_KEY: ${{ secrets.POSTHOG_QUERY_API_KEY }}
```

Result: `POSTHOG_QUERY_API_KEY browser-prefix match: false | assignment count: 0` — the gate stays green. The second layer does not catch it either: the bundle scan (`REPORT_CREDENTIAL_BUNDLE_FORBIDDEN`) greps for the literal *name*, and Vite inlines the *value*, so a leaked key would appear in `dist` as an opaque `phx_…` string that matches no pattern in the file. The `vite-env.d.ts` cases at `:449` and `:468` only require declared and referenced keys to agree — adding both satisfies them.

The leak still needs a second step (a production source must read the new key, since this build does not inline the whole `import.meta.env` object — confirmed absent from `dist/assets/*.js`), so this is a defense-in-depth gap rather than a present vulnerability. But the gate exists precisely to stop the arrangement one layer before the bundle, and it does not stop the most obvious arrangement.

**Fix:** assert on the value side as well as the name side, inside the Build `env` block:

```ts
const browserAssignments = [...buildEnv.matchAll(/^ +(VITE_[A-Z0-9_]+):\s*(.+)$/gmu)];
expect(browserAssignments.length).toBeGreaterThan(0);
for (const [, name, value] of browserAssignments) {
  expect(
    value,
    `${name} is inlined into a world-readable bundle, so it may only come from `
    + '`vars.*` — never from `secrets.*`.',
  ).not.toMatch(/secrets\./u);
}
```

### WR-03: The coverage gate pins a `defaults: 'unset'` claim the code now states is false

**File:** `scripts/verify-phase4-coverage.mjs:14`, with `src/measurement/posthog-lockdown.ts:27-33` and `COVERAGE.md:25`

**Issue:** Commit `b6e3576` (WR-05) corrected the lockdown's doc comment: `defaults: 'unset'` does **not** pin the date-gated default bundle — `'unset'` sorts lexicographically above every date literal, so it selects the **newest** branch of every gate other than `session_recording`. `measurement.test.ts:2058-2065` asserts exactly that.

The commit changed only `posthog-lockdown.ts` and `measurement.test.ts`. `REQUIRED_TABLES` at `verify-phase4-coverage.mjs:14` still **requires** a COVERAGE.md row literally titled `` `defaults: 'unset'` pinning of the date-gated default set ``, and `COVERAGE.md:25` still gives as its reason "a dated default set is a moving target, and `'2026-01-30'` or later enables `internal_or_test_user_hostname`" — while `'unset'` is precisely the value that selects that later branch. So `npm run verify:coverage`, which is now a **deploy gate** (`deploy.yml:59-60`), enforces on every push the continued presence of a capability claim the source code contradicts.

This is the inverse of the failure this repository's own convention names: not a claim that lost its gate, but a gate that outlived its claim.

**Fix:** rename the required row and restate its reason in the same commit, e.g. `` `defaults` sentinel and the date-gated default set `` with a reason recording what `'unset'` actually selects and that the three privacy-carrying date-gated keys are locked and read back. Update `REQUIRED_TABLES` and `COVERAGE.md:25` together, and cross-reference `measurement.test.ts#locks or acknowledges every date-gated default key the installed SDK carries` as the executable half.

### WR-05: `ships the unset provider bundle …` no longer scans an unset provider bundle in CI

**Issue:** The case's subject is `builtBundleText()` — the repository's `dist`. ### IN-02: `POSTHOG_QUERY_API_KEY` is not trimmed, while `POSTHOG_PROJECT_ID` now is

**File:** `scripts/generate-haoo-report.mjs:78` vs `:79`

**Issue:** WR-03's fix trims the project id with the recorded reason that "a trailing newline from a shell heredoc would otherwise reach the URL". The same shell produces the API key, which is read raw at `:78` and interpolated into `Authorization: Bearer ${apiKey}` (`src/reporting/generate.ts:274`). The emptiness check at `:129` uses `value.trim()`, so a whitespace-padded key passes validation and then produces an opaque 401 (or an undici invalid-header rejection) instead of the named, actionable error the rest of this CLI is built around.

**Fix:** `const apiKey = (process.env.POSTHOG_QUERY_API_KEY ?? '').trim();` — one line, same reasoning already recorded for the project id.

### IN-03: The chunk partition matches the vendor name against the full path, not the basename

**File:** `src/test/build-output.test.ts:373` and `:396`

**Issue:** `listFiles` returns absolute paths, so `file.includes('posthog-sdk')` tests the whole path. ### IN-07: Nothing asserts that merely *loading* the SDK is inert

**File:** `vite.config.ts:64-75`, `src/measurement/posthog.ts:57-59`

**Issue:** `posthog-js`'s module body is an IIFE (`node_modules/posthog-js/dist/module.js`: `_u=function(){…}()`): importing it sets `SDK_DIST_CHANNEL`, constructs a `PostHog` instance, and either calls `_dom_loaded()` immediately or registers a `DOMContentLoaded` listener. Because 04.1-09 chose a static value import, that vendor code now executes on **every** page load, including provider-unset builds where the adapter never calls `init`. D7's evidence ("0 invocations of the real `init`") covers only the test runner, and no gate asserts that evaluating the vendor chunk performs no network, storage, or capture side effect in a provider-unset build.

The privacy claim is still sound — the ingestion origin only reaches this project's chunks in a selected build, and no instance is initialized — but "the SDK is loaded, delivery is off" is currently a statement about `init`, not about module evaluation.

**Fix:** add one case that imports the SDK in a jsdom environment with `fetch`, `XMLHttpRequest`, `sendBeacon`, `localStorage` and `document.cookie` instrumented, dispatches `DOMContentLoaded`, and asserts zero calls to each. That converts the strongest claim this section makes into a measured one, and it will be the first gate to go red at a version bump that adds an import-time side effect.
