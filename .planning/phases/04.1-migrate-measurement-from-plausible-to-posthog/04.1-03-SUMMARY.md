## Decisions Made

- **Read the option surface from the SDK, not from a wizard scaffold.** When the wizard
  could not run, the alternative was not "skip the evidence" but "find the better source".
  `@posthog/types@1.408.0/dist/posthog-config.d.ts` ships inside the pinned tree and *is*
  the option surface at exactly 1.425.1; a wizard scaffold would have been generated code
  *about* it. The substitution strengthened the evidence rather than weakening it.
- **Add an import-graph prohibition for the new module (Rule 2).** The header comment
  claims no production module may import it. `APPROVED_SOURCE_MODULE_FORBIDDEN` makes that
  claim enforceable for the sibling module; without the analogue, the new module's claim
  would have been documentation. A second import route would publish the origin in the
  provider-unset bundle, which is exactly what the anchor exists to prevent.
- **Keep only the US ingestion origin.** Listing the EU origin "for completeness" would let
  a build be pointed at a region the visitor-facing disclosure (D-10) does not name.
  Absent beats present-and-unused.
- **Assert the frozen list's *shape*, not just its contents.** Each approved entry must be
  an absolute `https:` origin whose `URL.origin` round-trips and which carries no path,
  query, credentials or fragment — so a future entry cannot smuggle in a value a resolver
  might later treat as a prefix match.

## Deviations from Plan

### Auto-fixed / deferred issues

**1. [Rule 3 - Blocking] The wizard cannot run: it is an agentic installer needing credentials for an account that does not exist yet**

- **Found during:** Task 2
- **Issue:** `npx -y @posthog/wizard@latest` exits 1 with
  `PHW_CLI_INTERACTIVE_REQUIRED` — *"This installer requires an interactive terminal
  (TTY)… For CI/CD environments, use --ci mode: npx @posthog/wizard --ci --region us
  --api-key phx_xxx"*. `@posthog/wizard@2.71.0` is not a template scaffolder; it drives a
  coding agent against authenticated PostHog cloud "skills" (its `dist/agent-interface`
  carries the agent instruction set) and ships no static initialization template — a
  search of the whole package for a `posthog.init` scaffold returns only decorative TUI
  animation strings. It therefore requires a PostHog personal API key, and **D-09 records
  that no PostHog project exists yet**; account creation is deferred to 04.1-08's
  USER-SETUP work.
- **Fix:** The wizard was run once via `npx -y` exactly as approved, and wrote nothing —
  a `git status --porcelain` snapshot taken before the run and diffed after is
  byte-identical. Task 2's substantive deliverable and *every* acceptance criterion are
  independent of it, so the install proceeded. The wizard's sole intended contribution —
  "the observed initialization option names and the `defaults` date", explicitly *not*
  adopted as code — was taken from the pinned SDK's own shipped declarations instead
  (recorded under Accomplishments and coverage D7).
- **Not escalated as an auth checkpoint because** the credential would unblock nothing
  that survives: the wizard's output is reverted by construction, so blocking the phase to
  create a PostHog account now would buy a strictly weaker form of evidence than the one
  already obtained, and would pull D-09's owner-setup step out of the sequence the phase
  deliberately chose for it. No account was created and no credential was supplied.
- **Net effect on the threat model:** T-04.1-22 (wizard output tampering) closes more
  strongly than planned — there is no wizard output to revert, review, or trust.
- **Committed in:** `5a5e43f`

**2. [Rule 3 - Blocking] The selector-SET bundle assertion cannot fail until a reader exists — deferred to 04.1-04**

- **Found during:** Task 3
- **Issue:** Task 3 asked for a describe asserting *"with the selector set to the exact
  provider value the built bundle carries the approved origin exactly once"*. Vite
  substitutes a `define` only where a module **references** it. Measured directly:

  | Build | Constant has a reader? | Occurrences in `dist/assets/*.js` |
  |---|---|---|
  | `VITE_HAOO_MEASUREMENT_PROVIDER=plausible` | yes (`buildTimeApprovedScriptSources`) | `plausible.io` × 1 |
  | `VITE_HAOO_MEASUREMENT_PROVIDER=posthog` | **no** | `us.i.posthog.com` × 0 |
  | unset | n/a | both × 0 |

  Task 3 explicitly forbids touching `src/measurement/`, `src/products/` or
  `src/components/`, so this plan cannot create the reader.
- **Fix:** Implemented the half that is true and falsifiable — the selector-UNSET absence
  case — plus the source-derivation wiring assertions, which is what the *existing*
  provider-gated-selector case actually is (it reads `vite.config.ts` text; it is not a
  second build), so the mirror is faithful. Added direct selector assertions covering all
  the normalization cases the plan named. Deferred the presence case to 04.1-04 with the
  measurements above.
- **Why not assert it anyway:** it would have had to expect zero occurrences for a
  selector-SET build — passing for the wrong reason, and continuing to pass if the define
  were deleted outright. That is precisely the failure mode 04.1-01 established a pattern
  against.
- **Logged:** `deferred-items.md` D2. **Committed in:** `ac5c290`

**3. [Rule 3 - Blocking] `VITE_HAOO_POSTHOG_TOKEN` / `VITE_HAOO_POSTHOG_API_HOST` declarations deferred to 04.1-04**

- **Found during:** Task 3
- **Issue:** Task 3 asked for both keys in the exhaustive `ImportMetaEnv` interface, and
  an acceptance criterion requires `grep -Ec` to return 2. Adding them turns
  `it('declares no public build variable no production source reads')` red — measured, not
  predicted: `- []` / `+ [ "VITE_HAOO_POSTHOG_TOKEN", "VITE_HAOO_POSTHOG_API_HOST" ]` at
  `src/test/build-output.test.ts:339`. That invariant is bidirectional by design, and no
  production source reads either key until 04.1-04 adds the resolvers.
- **Fix:** Deferred both declarations to 04.1-04, to land in the same commit as their
  readers — the exact additive mirror of the discipline this plan already states for the
  subtractive side (*"04.1-04 removes the readers and what they read in one commit"*).
- **Why not widen the invariant:** it is the only build-time signal for a renamed or
  misspelled variable, which types as `any` under Vite's `ImportMetaEnv` index signature,
  compiles clean, resolves to `undefined`, and fails closed to analytics silently off.
  Loosening it to tolerate declared-but-unread keys would remove that signal permanently
  to satisfy one plan's grep count.
- **Note:** the build-time constant `__HAOO_APPROVED_ANALYTICS_HOSTS__` was **not**
  deferred — it is a `declare const`, not a `VITE_`-prefixed key, so neither direction of
  the exhaustiveness scan applies to it.
- **Logged:** `deferred-items.md` D3. **Committed in:** `ac5c290`

**4. [Rule 1 - Mis-specified criterion] `grep -c 'approvedAnalyticsHostsForProvider' vite.config.ts -eq 1` is unsatisfiable**

- **Found during:** Task 3
- **Issue:** The criterion expects 1; an ESM import plus a call site is necessarily 2.
- **Evidence it is the criterion and not the implementation:** the pre-existing, verified
  analogue `grep -c 'approvedScriptSourcesForProvider' vite.config.ts` also returns **2**.
- **Fix:** Satisfied on the criterion's stated intent — *"the new define is wired exactly
  once"*: `grep -c 'approvedAnalyticsHostsForProvider(env'` returns **1**, matching the
  analogue exactly, and there is exactly one `__HAOO_APPROVED_ANALYTICS_HOSTS__` define.
- **Committed in:** `ac5c290`
