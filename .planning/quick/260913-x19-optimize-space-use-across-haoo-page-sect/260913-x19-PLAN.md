<planning_decisions>
**PD-1: privacy notes stay inside the form (the orchestrator's contingency applies).**
- 02-UI-SPEC L226 and L389 lock the three-sentence disclosure note "immediately above the submit control". 03-UI-SPEC L77 and L149 lock the measurement details element "immediately after that visible sentence and before the submit control".
- The submit button's aria-describedby points at the collection note.
- Moving them into the left column would break all three.
- The left column therefore holds only the existing h2 and the two existing lead paragraphs, sticky at lg.
- No new copy is added, because new visitor-facing copy would need owner approval and the constraints keep locked copy byte-identical.
- The form gets shorter from the paired fields and from the wider card, where the note wraps to fewer lines.

**PD-2: field pairing is a product-generic rule, not a HAOO field list.** A Phase 2 decision says QualifyForm holds no HAOO field names. A field spans both columns when:
- its control is textarea, or
- it would otherwise sit alone in its row. That means the number of half-width fields since the last full-width field is even, and the field is the group's last field or is followed by a textarea.

For HAOO this yields exactly the owner's pairs, and timeframe and message span full width.

**PD-3: section split breakpoint.** The #qualify split is lg (1024px), per the orchestrator. At 1024 the right column is about 530px, so paired labels are the tightest there. If the visual check measures a pair whose control tops differ by more than 1px at 1024 or 1280, move every #qualify grid and sticky utility from the lg prefix to the xl prefix. Field pairing still starts at md. Record which breakpoint shipped.

**PD-4: brochure.**
- `BrochurePanel` shows the `<img>` only below lg. At lg it always renders `<object type="application/pdf">`, and the child fallback renders only when the browser cannot embed PDFs.
- Headless-shell Chromium has no PDF viewer. Default desktop Chrome, Edge, Firefox and Safari do.
- Real visitors can still reach the fallback, for example Android Chrome tablets at 1024 CSS px or wider, or Chrome with "Download PDFs" on.
- The fix is therefore proportional: the fallback fills the object frame as one centred card. No second image is added, because a preview image under "Brochure preview unavailable" would contradict the heading and duplicate the named preview image.
- The probe records pdfViewerEnabled in headless shell and in headed Chromium (DISPLAY=:0 is available; /snap/bin/chromium also exists).

**PD-5: e2e/viewport.e2e.ts PRODUCTS_CARD is NOT edited.**
- Its relationship value mirrors ZERO-PAPERHUB/src/products/registry.ts (HAOO_CARD), which is served on zero-paperhub.com. This task does not and cannot change that file, since verify:disjoint forbids it.
- Editing the fixture would break the live S3 assertion.
- The SUMMARY records it as a follow-up for the ZERO-PAPER HUB repository.

**PD-6: e2e scope.**
- Keyboard and semantics specs measure the deployed site and skip on preview. DOM order, headings and regions are unchanged, so no e2e spec edit is expected.
- The visual check proves the new layout's order, alignment and sticky behaviour against the preview build.
- If a preview e2e spec fails, fix the layout. Re-pin an assertion only when the failure is a direct result of an owner-requested layout change, and add a comment citing 260913-x19.
- Live e2e is not run: www.haoo.online still serves the undeployed page.
